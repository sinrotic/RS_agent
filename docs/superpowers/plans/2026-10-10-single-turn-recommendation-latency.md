# 单轮推荐 300ms 实现方案

对需求明确的单轮商品推荐增加直接执行的处理路径，复用现有召回、排序、偏好和商品事实，在真实业务链路上争取完整结果 P95 不超过 300ms。复杂对话继续使用现有 Agent。先取得真实依赖的分段基线，再实现路由、结果组装、缓存与展示优化；每阶段单独验证质量和延迟。

300ms 是待验证的目标。当前约 5 秒的隔离 Agent 压测不是在线商品推荐基线，不能用于承诺这次方案的收益。业务实现与服务部署在完成本方案前均不切换。

2026-10-10 实施状态：直接推荐、计算缓存、连接复用和服务器分段观测已实现，新增功能保持默认关闭。GPU 1 上真实 BGE HTTP 的短文本单请求约 68ms，8 并发最慢约 560ms；完整业务 300ms 门禁尚未完成。实现、原始数据与启用条件见 [本轮报告](../../reports/agent-recommendation-optimization-20261010/README.md)。

后续真实验收已补齐 Gateway、语义召回、训练排序、目录事实、最终持久化和浏览器展示。明确首轮鼠标推荐完整接口约 1.24–1.42 秒，浏览器约 1.37–1.90 秒；300ms 未达标。原 Agent 8 并发有 5 个约 30 秒超时，正式开关继续关闭。详见 [完整链路报告](../../reports/agent-recommendation-e2e-20261010/README.md)。下一阶段需优先处理恢复与多次持久化往返，保留最终提交边界。

存储阶段优化现已完成：显式 MySQL 连接池、投影短事务、商品批量插入、Redis 追加与 TTL 合并、同轮权威历史复用。最终预热完整接口 775–802ms，8 用户预热并发 1179–1347ms，真实浏览器完整显示 870–1363ms；历史恢复、重试和反馈已核验。300ms 门禁仍未通过，下一步需要细分提交与生命周期通知耗时，并设计可靠派生投影刷新。详见 [存储优化验收](../../reports/agent-persistence-optimization-20261010/README.md)。

## 目标和测量范围

第一版适用于首轮、需求独立完整的商品推荐：明确品类，可带能确定解析和核验的价格范围。只有句子全部被识别且商品事实可核实时，才走直接执行路径。初始品类白名单由真实目录与样本确定。

完整结果包括推荐商品、基于事实的简短理由、公开响应投影以及本轮持久事实。前端测量还包括 Catalog Item hydration 和 React 提交。单纯收到确认、首 token、提前显示卡片，以及失败或降级后的泛泛回答均不算完成目标。

初始验收负载为 8 个独立 Session 并发；随后测试 16、32 并发与混合复杂请求，报告每档实际可承受范围。服务器预热状态下，以不同新查询且未命中最终推荐结果缓存的样本验收 300ms；查询/评分缓存命中与未命中分别报告。冷启动、首次模型请求、同一 Session 内排队与正常空闲 Session 分别报告，不能静默剔除后者再声称所有请求达标。

端到端时钟从浏览器发送开始，到最终结果及商品展示完成为止；另测网关至 Agent `done` 的服务端耗时。网络位置和 RTT 必须随报告记录。图片二进制下载独立记录，不把图片未加载称为图片已完成；商品标题、价格等必要字段必须可显示。

## 现状

### 当前调用顺序

```text
浏览器发送消息
  → Gateway 身份校验
  → Session Execution Lane 与全局 active-loop 额度
  → 重试检查与 Session 恢复
  → recommendDelivery：非空 user_message 一律走 semantic-recall
  → 查询 embedding → 向量检索 → 商品事实回填
  → 价格过滤 → COLD/DeepFM → BGE 相关性融合 → 偏好与多样性
  → Recommendation Delivery 和推荐 trace
  → Agent Loop 的模型与工具往返
  → 公开 answer blocks 与 ASSISTANT_FINAL 持久化
  → SSE done
  → 浏览器批量请求 Catalog → 渲染结果
```

以上为当前配置启用对应排序能力时的代码路径。配置未启用或运行时不可用时会走其他路径，不能当作相同质量基线。

| 发现 | 对方案的影响 | 本地依据 |
|---|---|---|
| `executeTurn` 在模型执行之前已经取得推荐交付 | 可以研究直接组织推荐结果，避免必经模型往返 | `InMemoryAgentOrchestrationService.java` |
| HTTP 推荐适配器仅依据消息是否非空选择语义入口，约束来自 context | 需要保守识别意图并将完整价格约束传给推荐；不能假定模型事先处理了自然语言预算 | `HttpAgentRecommendationClient.java`、ADR 0015 |
| 语义召回与排序串行调用 embedding、向量、商品、COLD/DeepFM、BGE | 去掉 Agent 生成后仍须测这些真实环节 | `DefaultSemanticItemRecallProvider.java`、`TrainedAgentCandidateRanker.java` |
| BGE embedding 与 reranker 共用一把运行时锁，重排 batch_size 为 8 | 多个请求会在同一推理锁排队；HTTP 线程增加不等于模型并行 | `bge_m3_embedding_server.py` |
| 当前硬过滤主要为价格；部分 home 回退路径保留未知价格 | 快速路径要拒绝无法证明满足预算的商品；尺寸、材质等未实现核验的约束回退 Agent | `DefaultAgentRecommendService.java`、`TrainedAgentCandidateRanker.java` |
| Catalog 只提供数值 price，ProductCard 当前固定显示美元符号 | 先核实数据来源币种；人民币需求不能直接比较美元数值，不默认进行汇率转换 | `CatalogItem.java`、`ItemEmbeddingText.java`、`ProductCard.tsx` |
| 训练排序给出的 reason 是通用文字 | 不能将现有 reasonHint 直接当作充分的商品解释 | `TrainedAgentCandidateRanker.java` |
| 前端完成回调仅即时处理 A2UI，普通商品详情在 done 后请求 | 300ms 必须包含这次额外 HTTP 和渲染，或者实现兼容的完整展示数据返回 | `AgentChat.tsx`、`catalogHydration.ts` |
| 推荐通用 HTTP 读取超时为 20 秒，训练排序读取超时为 2 秒 | 当前异常延迟没有 300ms 的统一预算；快速路径要有独立截止时间和实际请求取消 | `RecommendationHttpConfiguration.java`、`RestTrainedRankingClient.java` |
| 当前 journal 同步写权威事件并更新可修复投影 | 初期保留持久化保证并纳入预算；不能将 final 异步写入后提前宣告成功 | `DefaultAgentSessionJournal.java`、ADR 0001 |
| 同 Session 串行、首版只有一个活跃 Agent 实例 | 快速路径沿用这些约束，横向扩容不属于本次方案 | ADR 0006、0007 |

相关代码位于 `java_agent/rs-service-agent`、`rs-service-recommend`、`rs-service-model`、`rs-service-catalog` 与 `frontend`。旧压测范围参见 [Agent 容量报告](../../reports/agent-capacity-20261009/README.md)；模型优化限制参见 [前期调查](../../reports/agent-recommendation-latency-20261010/research.md)。

## 实现设计

### 共用轮次生命周期

在现有编排中引入负责一次 Turn 执行的 Module，其小 Interface 接收已确认身份、当前 Runtime Profile、恢复后的 Session 状态及中断上下文，返回统一的轮次结果。Module 内部选择直接推荐或 Agent；调用方共用重试检查、语义事件追加、最终持久化、公开投影和完成响应。采用现有接口和数据结构的最小扩展，不为每个内部步骤增加公开接口。

Session Execution Lane、Account/Profile User 身份、client_turn_id 的同消息重试、失败轮次处理、Recommendation Delivery、finish reason 和历史恢复在两条路径上必须一致。正常与直接推荐路径都要服从 Profile 能力与公开 block allowlist。自定义提示词、未纳入验证的特殊 hook、需要处理的非空 A2UI 状态或未核验的运行时配置存在时，第一版不进入快速路径。客户端默认传入空 A2UI 状态不构成依赖上文。

在实际下游执行前建立可中断的轮次状态。截止时间与中断传到模型、HTTP 和工作任务；超时不能仅结束等待而让后台无限执行。最终提交与停止请求的竞争必须由共同生命周期处理，已经持久完成的 Turn 不能被事后改为 interrupted。

### 保守路由

第一版使用有限语法与真实目录品类映射，处理无需模型理解的独立推荐需求。不在请求前增加一次 LLM 分类，以免把模型延迟重新引入 300ms 路径。

| 请求 | 路由条件 |
|---|---|
| 给我推荐 300 元以内的双肩包 | 品类映射可靠、币种匹配且价格可核验时直接推荐；当前币种待核实 |
| 预算 200 到 300 元，推荐双肩包 | 币种匹配、上下限无冲突且支持该品类时直接推荐 |
| 300 元左右的双肩包 | “左右”缺少确定范围，第一版回退 Agent |
| 能装 15.6 寸电脑，防水，300 元以内 | 尺寸与防水未有标准属性校验时回退 Agent |
| 不要某品牌、比较两个商品、解释为什么适合我 | 第一版回退 Agent |
| 便宜一点、换一批、就按刚才的条件 | 依赖上文，第一版回退 Agent |
| 不推荐商品，只说选购建议 | 继续 Agent，避免无关召回 |

句子未识别的内容、否定、单位或币种歧义、多种预算、约束冲突，以及 context 和文本不一致均回退。数据币种只能由核验过的数据来源/目录配置确认，不能从界面固定美元符号反推。未支持的跨币种需求不自动换算，也不声称已满足预算。客户端传入的意图或置信度只可作为输入，不能直接授权绕过服务端核验。第一版只支持首轮；后续轮次需另行验证 Effective Context 和 Session Preference 的继承。

### 推荐与理由

复用当前 Recall Source 和 Ranking Route，保留已启用的 COLD/DeepFM、BGE 融合、在线偏好和多样性策略。不得靠禁用 BGE、减少 96 个精排候选、改融合权重或绕开效果门禁达到数字目标。

推荐 Module 返回完成状态、真实降级信息、可展示条目和内部约束验证依据。理由只引用已核验的目录属性和价格。例如只有币种匹配且价格确实小于等于预算，才说“价格在预算内”。推荐算法分数不是尺寸、防水或库存满足的证据。已有文字不足以形成有意义且可验证的理由时，保留候选交给 Agent，不重复召回或再次登记同一交付。

商品缺少硬约束事实时排除；不足时不要拿未核验商品补齐数量。空结果、推荐依赖不可用、排序降级和事实缺失分别处理与统计，不作为正常快速推荐成功。复杂回退继续现有能力，不删除工具。

### 展示数据

先保留现有前端 hydration，测它在目标网络下的占比。如果额外浏览器 HTTP 是关键瓶颈，再按 Catalog 权威数据生成 Display Product，作为最终公开响应的新增受限字段返回，前端优先使用；旧响应、历史恢复和数据缺失继续走原 hydration。

新增字段时同步修改公开投影、wire types、契约测试与 ADR 0012 的设计记录；不能把内部 Candidate Item、ranking evidence 或模型参数原样传给前端。推荐条目、显示卡片和反馈所用 card_set_id 必须一致。保留 A2UI、商品详情、反馈、停止、历史和重试行为。

### 缓存与并发

先缓存可重算的计算中间结果，再决定是否有必要缓存最终候选。每类缓存设条数或字节上限、版本与 TTL；同一缺失键只执行一次共享计算，同时支持等待者单独超时或取消，不让一个取消请求影响其他用户。

| 缓存 | 关键条件 |
|---|---|
| 查询 embedding | 精确查询与预处理版本、embedding 模型版本；仅安全的规范化，不合并否定或单位 |
| 语义召回 ID | embedding/索引版本、查询、召回参数与可见范围；不能将缓存 ID 当成当前商品事实 |
| BGE 分数 | 模型版本、查询、实际送入的商品文本内容哈希与截断规则；有变化重新计算 |
| COLD/DeepFM 分数 | Profile User、模型与特征快照版本、候选和受保护集合、阶段参数 |
| 最终候选如后续增加 | Account/Profile User、Session、偏好版本、全部约束、目录/索引/模型版本、输出数量与可见范围 |

价格与相关属性按现有 Catalog 权威及有效期获取；需要更严格事实新鲜度的字段另行制定刷新策略。没有可靠索引或特征版本时，不启用跨版本复用。缓存只存计算结果，不缓存 Recommendation Delivery 的 request_id；每次新的 Turn 仍生成当前交付并完成反馈归因。同 client_turn_id 的确认重试按已有事实精确重放，单独统计，不当成新推荐性能样本。

快速推荐和复杂 Agent 采用独立且有界的工作额度，沿用同一 Session Execution Lane。只做隔离而不无限增加并发；额外 HTTP 连接、任务队列与 CPU 推理数量需按实测设限。HTTP 连接复用、任务取消和截止时间先在快速路径验证，避免直接把全系统读取超时统一改成 300ms。

### 推理资源

BGE embedding 和 reranker 缺失是正式基线的前置条件。先核验权重、索引兼容版本与排序端点，修改启动器支持显式 device/GPU 参数；在服务器 CPU 的隔离进程上测相同权重的正确性、耗时和有限并发。计时区分请求排队、运行时锁等待与实际推理；按实测研究有最大等待时间的微批和模型调度，不能直接删除共用锁让线程争抢资源。CPU 无法满足预算时，如需要 GPU 推理，必须先形成 GPU 1 共存的显存/吞吐对照方案，证明不破坏现有复杂 Agent 容量；不能假定剩余显存足够，也不能占用 GPU 0、2 的训练资源。

量化已正式回退，APC 已开启、旧基线已关闭 thinking，本方案不把它们计算为新增收益。投机解码等仅属于后续复杂 Agent 优化，不作为直接推荐达到 300ms 的前提。若 BGE 的新查询与全量重排本身超过预算，则报告限制，重新评估推理资源；不能降级质量后仍标记达标。

## 300ms 的初始时间预算

以下是定位问题的设计预算，不是实测或各阶段 P95 的可加保证。最终仅由端到端测量判断达标。

| 阶段 | 初始预算 |
|---|---:|
| 身份、Session 调度、路由与输入核验 | 25ms |
| embedding、向量召回、候选事实 | 70ms |
| COLD/DeepFM、BGE、偏好与多样性 | 90ms |
| 交付登记、轮次持久化、结果投影与组装 | 45ms |
| 浏览器往返、商品补全与 React 提交 | 50ms |
| 余量 | 20ms |
| 合计 | 300ms |

若测得某个阶段超预算，先处理该阶段，而不是凭估计同时改动所有模块。空闲 Session 与争用 Session 的等待都计入各自结果。

- [ ] 若 hydration 显著影响端到端预算，实现最终响应的兼容展示字段、公开投影和前端复用，旧路径保留。
- [ ] 根据实测为快速路径分配额度与截止时间，优化 BGE 锁等待与有限微批，验证复杂 Agent 请求不会耗尽快速路径的工作额度。

主要改动：推荐/模型 HTTP adapters、内部计算缓存、公开响应与前端 hydration。每项先比较等价结果，再比较耗时。

### 阶段四 回归与有限启用

- [ ] 路由样本覆盖肯定/否定、预算冲突、单位、未知属性、不推荐商品、比较、依赖上文、特殊 Profile/A2UI/hook。
- [ ] 检查所有快路径结果的硬约束、目录事实、理由和排序；同候选/配置下排序策略保持一致，使用留出的样本验证质量。
- [ ] 检查不同用户和偏好版本的缓存隔离、反馈归因、同 Turn 重试、持久化失败、停止和历史恢复。
- [ ] 每个关键场景/缓存状态至少 1000 个完整新请求，主要档位重复三轮；采用固定到达节奏并记录等待，避免只用上一批结束才发下一批隐藏排队。
- [ ] 先测 8 并发，再测 16/32 与混合业务负载；记录 P50/P95/P99、完成率、约束违反、降级、回退、快路径覆盖率、吞吐与资源。
- [ ] 快速路径 8 并发完整结果 P95 ≤ 300ms、有效成功率至少 99%、验收样本无硬约束违反，且原功能回归通过后，有限启用配置。
- [ ] 未达标时保持原路由，并报告具体瓶颈；一次开关即可关闭直接推荐与新增缓存，不逆向修改数据库事实或训练权重。

缓存命中、正常未命中、超时、失败、降级、复杂 Agent 与同 Session 排队各自统计。失败与回退必须进入总体指标；只报告快速成功子集的低延迟不能代表系统整体 300ms。样本中零违规仅是验收证据，不等于所有未来请求绝对无回归。

## 实施前的判断

优先完成阶段一与阶段二。当前最大不确定性是 BGE 推理和真实持久化链路，而非 Java 中的少量对象创建。若相同质量的推荐依赖无法在预算内完成，300ms 只能先覆盖验证过的缓存命中或部分明确需求；覆盖比例必须公开，不能宣称所有单轮聊天都已经达到 300ms。
