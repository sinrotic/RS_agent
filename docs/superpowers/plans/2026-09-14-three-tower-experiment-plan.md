## 1. 实验问题与范围

目标是改善当前 Java 核心推荐链路的候选质量：Query 语义塔与 User 历史塔共享 Item 塔，联合学习语义相关性和行为偏好。先验证共享训练，再验证融合查询，最后评估 BGE-M3 微调。三塔数量本身不是验收指标。

当前首页已接入 epoch5 双塔、BGE 语义召回、多路协同召回、类目与探索；依据 [ADR-0019](../../adr/0019-trained-two-tower-home-recall.md)，双塔 serving 授权与旧 pool500 实验诊断状态不同。首页语义 query 来自历史/明确喜欢的商品文本；Agent 明确需求是另一类输入。两场景分别评估。

本计划先产出独立实验目录、数据版本、模型与离线报告；核心链路对照采用回放或只读影子评估。模型晋级时复用现有 Catalog、交付去重、反馈、多样性与降级逻辑。不会用旧双塔的离线数字替代 queryv2 serving 的重新评估。

要依次回答：

1. BGE 内容表示是否比原文本 hash 初始化更适合推荐？
2. 共享 Item 表示是否优于两个同条件、独立训练的检索模型？
3. User 和 Query 是否有各自贡献，尤其在当前需求偏离历史时？
4. 微调 BGE 比冻结 BGE 多带来多少收益，是否伤害语义能力？
5. 在相同候选预算及固定排序链路下，是否改善实际可展示的 Top-K？

## 3. 数据处理契约

### 3.1 行为样本

沿用原 UTC 半开时间窗：

- train：2021-06-15 至 2023-05-15。
- valid：2023-05-15 至 2023-06-15。
- test：2023-06-15 至 2023-09-14。

恢复目录缺少 `user_sequences.train.jsonl`。先核验远端匹配版本；没有可复用序列时，从 train 交互重建。采用哈希分片后每片排序或磁盘数据库索引，内存有界。排序键为 `(user_id, timestamp, stable_tie_key)`；同时间行为不互为历史。

样本字段：`sample_id/user_id/target_ts/history_item_ids/history_ts/target_item_id/label_policy_version/sample_weight/source_split`。构造历史前缀 → 后续正例。冷启动和少历史样本单独分桶；不要求所有 682 万用户都满足训练条件。

第一轮验证与测试均固定使用 train 截止的历史；不读取 valid 行为更新测试历史。之后若做滚动回放，必须另立协议，严格按事件时间更新，不能与静态结果混报。

负采样保留来源及概率。训练窗口内已知正例和重复商品做冲突屏蔽；不读取 valid/test 正例帮助训练屏蔽。不把所有未观察商品视为明确负反馈。先复用可审计的 batch 候选/采样方案，语义任务另设负采样器和温度。

注意已有 `user_interaction_count/item_interaction_count`、商品评分统计的时间来源未核实：第一版不用这些字段作为特征或负采样频率，频率从 train 重新计算。`exact_then_user_item_keep_last` 去重也需追溯执行顺序：若先跨全窗口保留最后一次，再切分，可能改变历史；无法消除时明确为回顾性去重数据限制，不能声称严格在线日志还原。

### 3.2 商品与候选域

统一 ID 为 parent_asin 对应的 Catalog Item 身份；核验在线 item_id 映射，不把评论 asin 的子变体当另一套主键。生成 `items.parquet` 或分片 JSONL，包含 item_id、文本字段、文本版本、来源、质量标志、去重分组。

文本模板优先标题、类目、明确 features，描述去 HTML/重复/模板噪声后补充；缺失描述可只用标题+features。不要补造静音、无线、价格或品牌等属性。评分、评论数、销量不拼入语义文本。商品元数据多为静态快照，缺少历史版本时披露此限制，不声称事件时点可见性已完整解决。

正式主评估域以 train-only 商品集合为上限；先对旧双塔、BGE、Catalog 做 ID 交集/差集审计。分别报告：

- 共同覆盖域：隔离模型本身的排序/匹配差异。
- 原始覆盖域与固定完整评估分母：包含缺失向量和不可查询用户，观察实际系统覆盖。

不通过只保留新模型容易命中的商品改善分母。候选集、过滤规则和 K 固定；额外报告去重前后及 Catalog 可回填覆盖。

### 3.3 语义训练样本

训练 query 从 train 商品的可验证事实生成；由商品组稳定分割 train/dev/test 来源，先分组再生成，近重复标题/同系列变体尽量同组。同一商品多条 query 均在同一组。推荐训练可能见过语义验证商品，标记为“未见 query 的传导评估”；若要测未见商品，再单设所有任务都排除该商品组的冷商品切片。

先选择 1,000 个覆盖主要类目/文本质量层次的商品，每件 2–3 条 query，共约 2,000–3,000 条试生成；通过质量检查后再扩至约 10,000 商品、20,000–30,000 query。规模是分阶段上限而非已生成数量。生成器先用项目可用模型/运行环境，确定模型版本和单条成本后执行，禁止在本轮直接调用线上批量生成服务。

query 类型包括中文自然需求、英文需求、属性约束、用途表达，保留 source_language；中英文改写归为同一意图组。首轮可约中英文各半，但最终按真实流量语言分布调整。避免完整标题复述、泄漏 item_id、仅凭品牌型号锁定商品。用途推断若不是商品事实，标记待审，不直接采用。

每行保存 `query_id/query_text/language/intent_group/source_item_ids/positive_item_ids/negative_item_ids/evidence_fields/generator_version/template_version/review_status/split`。正例可以有多个。通过 BM25、原 BGE 以及类目邻居提取候选，再核实相关性；未知属性不等于违反属性，不强判负例。困难负例选择“同类型但已知关键约束不满足”，先少量引入。

来源商品生成的 query–item 对属于合成监督，不能当真实点击。评论文字可以用于理解用户用语或另做蒸馏实验，但目标商品购买后的评论不作为该用户购买前 query 或历史输入。首轮不引入这类评论代理，避免新增归因问题。

### 3.4 独立语义验证与人工环节

先准备 120 条独立编写的 dev 需求，覆盖 6 个商品类型组、中文/英文、宽泛/约束/易混淆需求；按实际数据覆盖调整组别。第一轮由人审核至少 30 条及其候选池，确认任务与标注规则，再完成 dev。候选池来自各模型和 BM25 的并集，每条约 20–40 件，盲化模型来源，标注 0=不相关、1=部分满足、2=充分满足、unknown=证据不足。分歧条目复核，不把 LLM 判断称为人工金标。

最终确认实验前再冻结约 120 条独立 test 需求；与 dev、训练 query 及改写按意图去重，训练和调参不可读取其判断。人工标注工作由用户或指定评审参与；若暂时无人可审，可以做技术 smoke 和模型辅助诊断，但结论必须标为代理评估。

语义 Recall 只在已判相关集合上报告 `judged Recall@K`，不能宣称穷尽全库相关商品。同时报告 judged coverage；新模型引入未判候选时先补盲审，再比较 nDCG，不把 unknown 默认为负例。现有固定 fixtures 仅作为额外开发回归。

## 4. 模型与实验阶梯

首轮冻结 BGE，商品向量缓存 1024 维；轻量 Query/Item 投影输出 128 维，User 使用历史商品表示的有界聚合+MLP。用户和查询没有强制相互靠近的损失。先不用用户文字画像、不加 User ID 表、不同时替换序列模型；这些都是后续独立变量。

`L = lambda_sem * mean(L_sem) + lambda_rec * mean(L_rec)`。两个任务分别取 batch、定义正例与负例，并更新共享 ItemTower。先固定 1:1 的任务更新次数，比较 `lambda_sem:lambda_rec = 1:1、1:2、2:1`；记录每任务有效样本数、温度和梯度尺度，避免把 batch 频率变化误当 loss 权重收益。

| 阶段 | 实验 | 回答的问题与交付 |
| --- | --- | --- |
| P0 数据门禁 | 完整性、标签口径、时间/去重、ID 映射、模型资产审计 | 冻结 dataset manifest、样本 schema、split 与覆盖分母 |
| P1 基线回放 | 原 BGE、原 epoch5 queryv2、现有两路并集以及完整当前路由 | 建立本次真正可比的 baseline；旧指标仅为历史参考 |
| P2 单任务控制 | BGE+投影语义单任务；BGE 内容+User/Item 推荐单任务，两者使用独立 Item 参数 | 隔离文本表示升级、投影压缩和新训练器的收益 |
| P3 联合冻结 BGE | 与 P2 相同输入、维度和训练预算，两个任务共享 Item 参数；先保留两路检索 | 识别联合共享的增益或负迁移 |
| P4 融合查询 | 对 P3 比较两路并集与请求侧 `alpha*q+(1-alpha)*u`；相同唯一候选预算 | 融合是否有用，是否被历史带偏；alpha 先固定网格 0/0.25/0.5/0.75/1 |
| P5 BGE 微调 | 独立分支开放末层或 LoRA；先比较语义单任务微调，再比较联合微调 | 微调本身和联合训练分别带来什么；只训练 dense 路径 |
| P6 扩大与路由回放 | 达标配置扩大训练、最终 test、固定粗排/精排/反馈/探索的链路比较 | 给出离线采用/继续诊断/否决结论，单独准备上线候选 |

P0/P1 未通过不能进入正式效果实验。P2 到 P3 必须使用相同训练用户、样本、负例预算、候选域、向量维度与随机种子；独立双模型和共享模型的训练计算量与参数量都报告，不宣称完全相同。每次只改变一类主要因素。

程序 smoke 可用现有 1,000 用户切片。效果 pilot 从 train-only、按用户稳定 hash 选约 100,000 个可产生前缀样本的用户，并按历史长度、目标类目、热门/长尾分桶检查；不足时记录实际数，不通过 valid/test 选择训练用户。每用户最多 20 个训练前缀，历史最多 50 件为初始值。不要从文件前 100,000 行直接取样。

pilot 固定 5,000 个 valid 用户，入选仅使用 train 历史条件及稳定 ID 规则，统一保留无向量和无查询用户；晋级再用更大冻结 valid 集。首轮 1 个种子筛配置；候选方案与关键基线至少 3 个种子复验。全量训练只在 pilot 有方向性收益后启动。

BGE-M3 的官方模型卡提供 dense 微调入口，首版不引入 sparse/ColBERT 多种检索目标：[官方模型卡](https://huggingface.co/BAAI/bge-m3#faq)。LoRA/末层解冻是本项目候选实现，具体依赖版本、模块名、可训练权重和梯度连通性在 P5 小样本中验证，不预先宣称已兼容。

**微调时的梯度与缓存：**静态向量缓存仅适用于冻结 BGE。P5 不得一边声称 item 编码器被推荐损失训练，一边始终使用 detached 的旧商品缓存。正负候选商品须由可微前向编码或明确采用分阶段刷新策略；历史可采用缓存特征，但记录它是固定/延迟更新的历史输入。先用有界历史与候选数验证显存及梯度，再扩大。每次编码器变更重新编码商品并建版本化索引。

## 5. 指标、同质化检查与调整规则

推荐：Recall@100/500、HitRate@500、nDCG@100，用户宏平均和事件级分母分开；按历史长度、商品频次、类目、覆盖内外分桶，报告 queryless rate、候选不足和唯一命中。

语义：nDCG@10、judged Recall@50、明确约束违反率、judged coverage，中文和英文分开。首页由历史构造 query 的 next-item 召回单独统计，不能替代真实需求语义指标。

同质化/互补性：

- 固定用户切换 query：不同商品类型和同类型不同属性，检查结果是否跟随当前需求。
- 固定 query 更换历史：保持相关性的前提下比较偏好变化；无真实配对标签时只算受控行为诊断，不称个性化收益。
- 用 q-only、u-only、双路并集、融合向量做消融；用户历史置乱检验用户信号是否有效。
- Top-K 重合率、向量方差/有效秩、每任务在共享参数上的梯度方向作为辅助诊断，不能仅凭 cosine 接近判定塌缩。
- 特别设置“历史偏好与当前需求冲突”的独立语义用例。

路由：固定总候选预算、各旁路来源预算、过滤及排序模型版本，对照“当前完整路由”和“仅替换语义+双塔后的路由”。记录其他来源未命中的独有正例、最终 Top-K 质量、回填覆盖、延迟 P50/P95、显存/内存及建库成本。单模型超越旧双塔不能替代超过现有两路并集的证据。

首版继续扩大门槛：至少一个主指标相对提升 3%，另一任务主指标相对下降不超过 1%；独立语义集约束违反率不能显著恶化。以上为预先建议阈值，P1 看到基线和标注规模后可以调整一次并冻结。逐用户/逐意图组做配对 bootstrap 95% 区间；相关改写必须同组抽样。区间不确定则补评估数据或标记待定，不能判胜。

诊断后的调整：

- 语义好、推荐差：先检查采样、稀疏/覆盖和监督触达，再调任务权重；不要直接扩 BGE。
- 推荐好、语义差：降低推荐任务对共享层的影响、增加语义重放或更少解冻；必要时比较共享底层+独立 item projection（两个索引），明确放弃单索引假设。
- 单任务好、联合差：查梯度冲突和负例口径，保留独立两路作为有效结果，不强求三塔。
- 两任务好、融合差：保留共享训练+两路检索，不强行合并 query。
- 离线好、链路差：先查候选预算、Catalog 覆盖和下游压缩，不直接重训。

## 6. 资源、可复现与执行顺序

本机按 12 GB 可承受、14 GB 上限；流式读取、磁盘分片、mmap 数组，避免 Python dict 持有全用户/商品向量。448,282×1024 的 FP16 原始矩阵约 0.92 GB，864,288×1024 约 1.77 GB；仅为矩阵字节数，不含模型、梯度、索引和解释器开销。禁止据此推断完整训练内存安全。

冻结 BGE 先批量编码到独立缓存（远端执行前核实 GPU 是否被线上 embedding/reranker 占用，避免共用生产进程）。P5 远端独立实验进程，从小 micro-batch、256/512 文本 token、梯度累积和峰值测量开始，显存上限按实际设备与线上余量确定。具体训练时长和 GPU 费用在 P0 资源审计后估算，当前不编造总时长。

每次 run 保存 config、数据/文本/分割/负采样版本、源文件校验和、模型权重与 tokenizer 版本、代码版本和脏工作区补丁摘要、seed、task loss、梯度/资源统计、checkpoint、覆盖、分桶指标、ANN 与精确检索一致性。新模型需在固定样本上验证训练 encode 与导出/在线 encode 数值一致，不沿用已知不等价路径。

建议新目录：`python_agent/data/processed/three_tower_v1/`、`python_agent/outputs/experiments/three_tower/<run_id>/`。只记录路径建议，本轮尚未创建训练数据集或模型目录。

执行清单：
