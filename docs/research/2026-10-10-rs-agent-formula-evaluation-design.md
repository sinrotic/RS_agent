# RS_agent 公式评测集设计稿

日期：2026-10-10。本文把商品匹配评测具体化为数据结构、公式、样例和构造流程。公式及权重是项目设计建议，尚未经过真人偏好校准；示例商品为明确标记的演示数据，不是实际 Catalog Item 快照。没有修改现有评分实现或运行真实 Agent 实验。

来源核查另见 [ShoppingBench 公式审计](2026-10-10-shoppingbench-formula-audit.md)，整体方案见 [评测集起步方案](2026-10-10-rs-agent-evaluation-dataset-plan.md)。

## 1. 采用什么思想

ShoppingBench v4 的商品相关性公式为：

\[
r_{pro}=\frac{\mathbf{1}[sim\geq0.5]+\mathbf{1}[min\leq price\leq max]+|F_t\cap F_p|}{2+|F_t|}.
\]

论文比较推荐商品与标注目标商品的标题、价格范围及特征，还分别给出平均相关性 CAR 和严格成功率 ASR。它不是直接把用户原句与商品标题的相似度当作全部推荐质量。[论文 §Evaluation](https://arxiv.org/html/2508.04266v4)

RS_agent 采用相同的“可验证条件转分数”思路，但把标准对象设为用户需求：

```text
结构化需求 + 固定商品事实
→ 每件商品的可行性与偏好满足度
→ 推荐列表的约束通过情况与排序质量
```

同一需求可能有多个正确商品。生成任务时抽中的商品只是证明任务有解的一个见证，不能成为唯一正确答案。

## 2. 第一版范围

第一版只评 **明确需求推荐** 和 **反馈后的需求匹配**。输入中有可标注的商品需求，输出中有实际推荐的商品 ID，评分器根据固定目录和本轮工具证据评分。

解释的事实性、是否应该澄清、界面质量是其他任务类型。不能让这些任务统一套商品匹配公式，也不能因此惩罚合理的提问或无解回应。

推荐排序服务的 `score` 和模型自报的匹配度不是真值。评分器独立读取 Catalog Item/评测快照，不信任被测 Agent 写出的商品属性、分数或“全部条件已满足”断言。

## 3. 本地字段如何成为评测事实

当前 [CatalogItem](../../java_agent/rs-service-catalog/src/main/java/com/sinrotic/rs/catalog/domain/entity/CatalogItem.java)、[详情 VO](../../java_agent/rs-service-catalog/src/main/java/com/sinrotic/rs/catalog/domain/vo/CatalogItemDetailVO.java) 和 [目录表](../../java_agent/sql/rs_service_catalog_schema.sql) 已有 item_id、类目、品牌、价格、description 与 attributes。attributes 是字符串映射，尚不是统一的领域属性体系；price 没有独立 currency 字段。

建议在评测快照增加规范化事实投影，而不直接改业务目录：

| 字段 | 处理规则 |
|---|---|
| item_id | 稳定标识；不存在 ID 不可推荐；保留来源 ID |
| category | 规范类目 ID/树路径；按层级判定，不靠标题出现某个词 |
| price | 最小货币单位整数或 decimal；币种必须由已确认的来源/快照 manifest 给出 |
| brand / store | 同义名归一；保留原始字段；只有任务需要才评分 |
| 布尔属性 | true、false、unknown 三态；缺字段不等于 false |
| 数值属性 | 统一单位，例如 g、L、cm；原值和转换规则可追溯 |
| 属性证据 | 记录源字段/原文位置、提取方法、审核状态与快照版本 |

`wireless=false` 不能被包含“wireless”一词的长标题覆盖；“不支持蓝牙”不能被关键字匹配判成支持。`water resistant` 与 `waterproof` 也不能随意合并。

币种不明的记录暂不生成预算任务。不能把 Amazon 来源的一个价格数值直接按人民币解释。商品状态 active 也不证明实时库存或配送承诺，这些条件只有在固定环境有可靠事实时才加入任务。

模型可以协助提取文本属性，但正式标签需验证。计算公式只把已有标签变为分数，不能使未经核实的属性自动成为真值。

## 4. 用户需求：人工认可的 oracle

每个任务保存三份信息：

1. **Agent 可见输入：**用户自然语言、截至当前 Turn 的 Session 信息与可见画像。
2. **固定环境：**目录快照、工具实现/结果事实和初始状态。
3. **评测专用标签：**规范需求、硬/软条件、权重、有效范围、期望结果及审核依据。

示意结构如下；这是设计形状，不是当前实现支持的配置格式：

```yaml
id: demo_headphones_001
family_id: demo_headphones_goal_001
source: synthetic_demonstration
task_type: recommend
input:
  user_message: "推荐两款无线耳机，最多300元。黑色优先，重量尽量接近150克，300克以上就不考虑轻便性了。"
environment:
  catalog_snapshot: demo_catalog_cny_v1
oracle:
  target_count: 2
  price_scope: per_item
  hard_constraints:
    - {field: category_id, operator: is_a, value: headphones}
    - {field: price_minor, operator: lte, value: 30000, currency: CNY}
    - {field: wireless, operator: eq, value: true}
  soft_preferences:
    - field: weight_g
      scoring: prefer_lower_linear
      full_score_at_or_below: 150
      zero_score_at_or_above: 300
      weight: 0.6
    - field: color
      scoring: categorical_match
      value: black
      weight: 0.4
  expected_outcome: recommend_feasible_items
  review_status: demonstration_only
```

正常自然输入可以更简短，例如“希望轻便，黑色优先”。此时轻便函数的锚点及两项权重属于人工校准的偏好模型，不是用户原话中的数学真值。第一批尽量选择可明确标注的需求；对含糊表达，不凭空增加硬阈值。

评分需求不能由被测 Agent 自己解析后当作 gold。任务先有结构化目标再生成措辞，或由独立审核者从真实用户输入标注。人工确认自然表达没有遗漏、反转或新增条件。

## 5. 单件商品公式

### 5.1 硬约束：先判断可行

给用户需求 u、商品 p，定义每个硬条件：

\[
h_j(u,p)\in\{1,0,?\}.
\]

1 表示有事实支持满足，0 表示明确违反，? 表示无法核实。可验证的可行性为：

\[
H(u,p)=\mathbf{1}[p\text{ 存在于固定目录}]\prod_{j\in\mathcal H_u}\mathbf{1}[h_j(u,p)=1].
\]

“必须无线”但没有无线字段的商品不能被认证为满足。报告仍区分违反和未知，不能把未知描述成商品确实不支持。

商品存在于目录和 Agent 有合法工具证据是不同条件。后者在任务门槛中检查：当前推荐来自允许的工具结果/可信上下文；目录里确有其商品，也不能为模型凭空得到 ID 开绿灯。

### 5.2 软偏好：固定权重的部分得分

对每项软偏好定义 \(s_k(u,p)\in[0,1]\)，例如：

\[
s_{color}=\mathbf{1}[color=black],
\]

\[
s_{light}=\operatorname{clip}\left(\frac{300-weight_g}{300-150},0,1\right).
\]

该轻便函数来自这个演示任务的 150g/300g 锚点，不是通用耳机标准。数值锚点和权重在任务版本中固定，经人工偏好校准后才进入正式集合。

\[
U(u,p)=\frac{\sum_{k\in\mathcal S_u}w_k s_k(u,p)}{\sum_{k\in\mathcal S_u}w_k}.
\]

有软属性未知时，记其已确认效用下界为 0，保留原权重；禁止删除未知项后重归一，否则数据越缺可能分数越高。可同时记录效用上界 U+ 与已知覆盖率，检查是否因数据缺失影响排序。没有软偏好时定义 U=1。

### 5.3 商品匹配得分

\[
r(u,p)=H(u,p)\,U(u,p),\qquad ItemScore=100r(u,p).
\]

超预算、错品类或不满足必须属性的商品得 0，其他软偏好不能抵消。分项 H、U、unknown_count 必须保留：满足全部硬约束但不符合软偏好，与违反硬约束都可能 r=0，诊断原因不同。

匹配分刻画声明的需求满足度，不等于实际购买概率或真人满意度。尤其不自动奖励更低价格，除非用户明确把便宜设为偏好。

## 6. 推荐列表：数量、排序与整体门槛

只评平均分会让系统选择只返回最好的一件。第一版用任务明确的目标数量 K，例如用户确实要求“两款”，而不是给所有任务暗设 K=5。

固定可行集合：

\[
\mathcal F_u=\{p\in\mathcal C:h_j(u,p)=1\text{ 对全部硬条件成立}\}.
\]

这里 C 是冻结评测环境的目录全集。任务作者从全集验证目标，不从 Agent 实际返回的列表构造理想答案。再定义可能可行集合 F+：所有硬条件都没有被事实明确否定的商品集合；它包含已确认可行的 F，也包含某些关键事实未知的商品。

有足够符合要求的商品时 K 个位置固定。缺位为 0；重复商品的重复位置为 0；不存在/违规商品为 0；不提前移除错误位置以让后面的商品递补升位。

\[
DCG@K=\sum_{k=1}^{K}\frac{r(u,p_k)}{\log_2(k+1)}.
\]

\[
IDCG@K=\max_{\substack{L\text{ 为 }\mathcal F_u\text{ 中不同商品的有序列表}\\|L|=K}}DCG(L),\qquad Q@K=\frac{DCG@K}{IDCG@K}.
\]

该式使用线性 gain r，是借用 DCG 思路的项目指标。实现时从固定全集的独立评分排序求 IDCG。相同效用的顺序交换不惩罚。Q 有排序差异，但只在需求允许多个有效结果时使用，不强迫与生成任务时的种子商品一致。

任务整体门槛 G 同时要求：

- 数量满足任务的明确要求或明确允许的短缺回应；
- 主要推荐商品不重复且有合法来源；
- 所有实际推荐的商品均满足硬约束，包括超出 top K 的额外推荐；
- 该任务必须的回答/动作完成，未发生预先定义的严重违规。

推荐任务得到：

\[
Success(u,L)=G(u,L),\qquad TaskScore(u,L)=100G(u,L)Q@K.
\]

同时保留未乘 G 的 Q 和分项结果给优化器定位失败。整体门槛防止用很多高分商品稀释一个违规商品，Q 提供合格方案之间的改进信号。

特殊情形必须单独处理：

- \(|F_u|<K\)：构造时明确“返回所有可验证可行商品并说明不足”，或换成普通有解任务；不能隐瞒数量不可满足。若 F+ 还有未确认商品，不得声称全目录确实只有这么多可行商品。排序按该任务已定义的数量计算。
- \(|F^+_u|=0\)：每件商品至少有一项硬条件被明确否定，做 no_match 任务，验是否准确说明无解和可选择的放宽条件，不计算 Q。
- \(|F_u|=0\) 但 \(|F^+_u|>0\)：只能证明无法确认，不能证明全目录无解；任务类型改为 uncertain_match。
- IDCG=0：不除零，也不默认为 100%；报告排序不适用。若用于优化软匹配，应改进样本或偏好标签，确保固定全集有正效用商品。
- 套餐、同店、总预算和优惠券：跨商品依赖不能独立 top K 求最优；另定义合法商品组合和组合验收。首版先不混入这类任务。

可额外计算“已返回候选中的最优选择”用于诊断召回还是选择出错，但不能以 Agent 自己返回的候选集合取代主指标的固定全集，否则返回一个差候选也可自称最优。

以下五件商品均为演示数据，币种 CNY、品类 headphones；目标是两款、无线、单件≤300，轻便 0.6、黑色 0.4。

| 商品 | 价格 | 无线 | 重量 | 颜色 | H | U | ItemScore |
|---|---:|---|---:|---|---:|---:|---:|
| A | 260 | 是 | 150g | 黑 | 1 | 1.0 | 100 |
| B | 290 | 是 | 225g | 黑 | 1 | 0.7 | 70 |
| C | 320 | 是 | 100g | 黑 | 0 | 1.0 | 0 |
| D | 180 | 否 | 150g | 黑 | 0 | 1.0 | 0 |
| E | 220 | 是 | 225g | 白 | 1 | 0.3 | 30 |

| 最终推荐 | Q@2 | Success | TaskScore | 解释 |
|---|---:|---:|---:|---|
| A,B | 1.0000 | 1 | 100.00 | 两件都合格，偏好满足度最佳 |

## 8. 多 Turn 标签更新

每个 Turn 有截至当时已表达的有效需求 u_t。用户新说“预算改成200”，只替换该预算，其他仍有效条件保留；明确撤销或更换品类时才修改相应条件。

\[
u_t=Update(u_{t-1},\text{截至 Turn t 的已表达反馈}).
\]

这个 Update 是任务作者提供的 oracle，不信任被测 Agent 的解析结果。当前请求优先于冲突的旧画像。未来用户才披露的条件不得提前加入 u_t。

逐 Turn 计算硬通过情况与 r/Q，可获得约束保留率：

\[
Retention=\frac{\text{后续确实遵守的未撤销条件数}}{\text{该后续任务要求检验的未撤销条件数}}.
\]

若没有适用条件，记 N/A。用户对刚否定的商品明确要求比较时，不能机械按“重复拒绝商品”判错。第一版优先固定前缀的反馈任务；完整 Session 需要按 Agent 实际行为分支的用户环境。

## 9. 第一批评测集怎样构造

建议流水线：

1. **冻结目录小样本。** 先覆盖少数事实充分的品类；选实际可取得的记录，不导入整个商品库。记录来源、币种和属性质量。
2. **规范事实。** 做类目、单位和属性词汇映射；保留原文证据。缺字段保留 unknown。
3. **生成结构化目标。** 从可验证属性选出硬条件和少量软偏好；先计算 F 和 IDCG，证明任务可解、具备区分度。
4. **加入干扰商品。** 包含便宜但必须属性不符、属性匹配但超预算、满足硬条件但软偏好一般、属性缺失等商品。
5. **生成用户自然表达并审核。** 不泄漏商品 ID/标签，不遗漏硬条件，不把软偏好说成必须；中文需求和英文目录属性用独立规范词汇连接。
6. **加入真实用户任务与反馈。** 有真实表达时由独立标注者补 oracle。用户反馈任务固定初始 Session 和工具事实。
7. **先分组划分，再扩增。** 同一目标、原 Session 和商品种子派生的问题族放同一 split。改写不能增加独立样本计数。
8. **验证评分器反例，再跑基线。** 先验证超预算、不存在 ID、重复、漏数量、unknown 等能被公平处理，再接当前 Java Agent 和真实模型。

40 个独立种子的暂定覆盖：20 个明确约束匹配、10 个预算/属性反馈、5 个否定/排除条件、5 个无解或无法确认任务。这个分配是起步建议；最终通过率按任务类型分别报告，不能混合它们不适用的 Q。

建议第一批目录规模约 100–200 个经审核的记录，实际按可取得的数据质量调整。很多商品、很多改写不自动意味着有代表性；之后再增加真实用户、品类和新的时间窗口。

## 10. 判断 Skill 是否改善

同时报告硬成功率、合格推荐排序/匹配分、具体违反条件、unknown 覆盖、运行失败与成本。不要只看合格任务条件均分，因为失败多的系统可能靠筛掉难题提高它。

推荐任务可在同一固定集合报告均值 TaskScore（失败计0）与成功率；no_match、uncertain_match、解释和澄清另报自己的结果。阶段性统一比较可先用预定分层权重的任务成功率，避免把定义不同的分数随意相加。

旧版与候选在同样的任务和环境配对运行。优化器获得优化集的分项失败，如“预算遵守了但丢失无线要求”或“全部硬条件通过但偏好次优”；正式选择标准和权重固定。评分器、oracle 和隐藏测试不由优化器修改。

第一版公式评测能让商品事实和声明需求之间的改善可见。真人满意度、无谓追问、解释帮助和线上选择仍需单独验证，不能由这个匹配分推导出来。
