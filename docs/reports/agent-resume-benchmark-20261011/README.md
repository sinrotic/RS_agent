# 简历指标补测：完整推荐与多并发

本轮按“使用没有出错的例子，补测单并发与多并发平均，并选择收益最明显的简历指标”的要求执行。测试先固定档位和重复数，保留全部失败；成功配对按同档、同批、同位置、同测试账号匹配，不按单条速度选取样本。性能对照正式请求每组 104 条，另外保留两组预热与最初构建的筛查。

## 最适合写入简历的结果

> 优化 Java Agent 推荐服务的并发编排与模型量化，在预热后的真实普通推荐压测中，将单并发完整推荐平均耗时由 3.37 秒降至 2.35 秒，降低约 30%；在 16 路独立会话突发测试中，将合格完成吞吐量由 0.70 提升至 1.36 次/秒，提高约 95%，完整通过率由 23/48 提升至 48/48。

耗时指标每组 8 条，全部通过；16 路指标每组 3 批、共 48 条，是突发实验观察值，不是生产稳定吞吐或持续最大并发。这里只比较本轮模型量化及最新并发编排前后，不代表最初版本到最终版本的全部收益。上述正文可用于描述普通推荐，不能推广到复杂推荐或多轮所有场景。

## 全部结果

| 同时发起的请求数 | 旧版完整通过 | 新版完整通过 | 旧版成功样本平均完整耗时 | 新版成功样本平均完整耗时 | 旧版→新版合格完成吞吐 |
| --- | --- | --- | ---: | ---: | ---: |
| 1 | 8/8 | 8/8 | 3.368 秒 | 2.349 秒 | 0.2950 → 0.4220 次/秒 |
| 4 | 16/16 | 16/16 | 3.880 秒 | 3.345 秒 | 0.8763 → 1.1280 次/秒 |
| 8 | 30/32 | 32/32 | 7.168 秒 | 8.062 秒 | 0.5236 → 0.9159 次/秒 |
| 16 | 23/48 | 48/48 | 6.953 秒 | 10.421 秒 | 0.6955 → 1.3551 次/秒 |

两边全部成功的档位中，单并发平均耗时降低 **30.26%**，4 路降低 **13.79%**。8 路合格吞吐增加 **74.92%**，16 路增加 **94.84%**；吞吐为各批合格数量之和除以各批墙钟时间之和，不取最好一批、不平均每批吞吐。

8 路成功配对共有 30 对，配对平均为 7.168 → 8.094 秒，增加 12.91%；16 路成功配对共有 23 对，配对平均为 6.953 → 10.281 秒，增加 47.87%。它们仅描述“两边均成功”的条件子集，不能作为所有请求体验。上表成功均值的分母在 8、16 路不相同，因此同时提供了匹配后的均值。不能宣称高并发下单条请求普遍更快。

旧版正式测试共 24 条 AGENT_BUSY、3 条排序降级；其中 8 路降级 2 条、16 路降级 1 条。新版 104/104 完整通过，无失败工具及上述降级。旧版成功样本总数为 77/104，但不能把同档不同模型、不同完成数量的整体均值混算成某个“全场景加速”比例。

正文长度也是解释边界：单并发旧版平均 189.50 字，新版 184.63 字，均值接近；8 路旧版成功正文平均 92.87 字、新版 177.22 字；16 路为 98.74 → 171.60 字。输出随机性、正文长度与承接更多请求都会影响并发耗时，本轮没有逐条人工评定理由语义，不能证明语义质量完全相等。

## 对照对象及测量口径

- 旧版 Agent：最新并发改造之前的 `8a8385f3ee802ed38333ffc49bd43a6306b97b5d829e013b433ce75a9179fa03`，已经包含普通推荐的 LLM 合成；模型流 8 路、等待 200ms。
- 新版 Agent：`4bc94fc6894a65fb933071ac91c2506c5964542c68d464f59155967c027c1c76`，模型流 16 路、等待 15 秒、推荐许可 4 路。
- 旧模型为原 Qwen3.5-4B BF16；新模型为当前 MLP INT4、注意力/GDN BF16 权重。两组均在 GPU 2 的同一 RTX 4090 顺序启动，不切换 GPU 1 线上模型。
- 两组 vLLM 启动参数统一：显存预算 50%、最大序列 32、上下文 16384、前缀缓存开启、xgrammar 紧凑 JSON 输出、同工具解析器和采样环境。序列上限为本任务测试配置，线上模型的 128 上限没有改动。
- 使用真实账号、画像、目录、推荐服务、DeepFM/BGE 和持久历史；统一请求“推荐鼠标”，每条 limit=5。单并发均为同一测试账号，4 路为 4 个账号，8/16 路为 8 个账号；16 路是 16 个独立 Session，不是 16 个不同账号。
- 单并发 8 次，4 路和 8 路各 4 批，16 路 3 批，两组各 104 条。组内所有正式结果保留；预热单独列出。组间顺序为旧 BF16 后新版量化，未随机交错模型，GPU 2 其他任务与共享下游负载未完全控制。
- 完整耗时从测试客户端提交独立 Agent 的 SSE 请求开始，直到最终回答与真实目录商品补齐。不包括登录、创建 Session、浏览器绘制或公网入口；随后历史/追踪核验不计入单条完整耗时，但计入整批吞吐墙钟。
- 完整通过要求最终回答、五个真实且唯一的商品、非空正文、持久历史 FINAL_ANSWER、工具无失败、DeepFM/BGE 排序均执行、无排序降级。它是结构及流水线检查，不替代语义人工回归。

所有正式单并发/4 路窗口两组分别观察到 8/16 次模型调用；新版 8/16 路分别为 32/48 次，证明测量范围包含真实模型生成。旧版 8/16 路分别有 45/30 次模型调用，部分降级请求触发额外模型循环。每批原始模型指标保留在 JSON；不将并发缓存查询计数直接当作唯一命中的输入 token 数。

## 初始化、预热与清理

首次使用原 BF16 78% 预算被资源余量检查拒绝，未启动模型；统一 50%/128 序列的尝试因 BF16 Mamba 缓存块只有 57、无法捕获 128 序列的 CUDA 图而失败。两次过程分别保存为 `workflow-resource-guard.json` 与 `workflow-initialization-failure.json`。随后将两组临时序列上限都设为 32，成功执行全部正式测试。未安装依赖或改动共享模型启动参数。

BF16 控制组预热完整耗时 6.425 秒，量化新版预热 13.363 秒，单独记录，不计正式均值。初始化、模型加载、首次编译及失败不计入业务热态性能。结果不能用于保证刚启动后的首次请求延迟。

最终 `audit.json` 验证 GPU 1 模型与共享服务身份未变、六个服务健康 UP、本任务容器及私有环境副本消失、临时模型进程组清理、18319/18096 关闭。GPU 0 训练及 GPU 2 其他任务未被本任务停止。模型状态和 GPU 快照保留，未下载账号、令牌、原始模型输入或回答正文。
