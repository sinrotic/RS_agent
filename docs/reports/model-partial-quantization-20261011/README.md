# 部分 INT4 / BF16 工具调用对照（2026-10-11）

后续服务优化已实测并全部撤回，当前仍为本报告的 50% / 128 部分量化配置，启动与预热脚本也已恢复原摘要。最新运行 PID、原配置核验及未推广原因见 [服务优化执行记录](../model-serving-next-optimizations-20261011/execution.md)。下面的部署/扩容 JSON 是各阶段历史证据，旧 PID 不是当前 PID。

最新正式配置是 MLP INT4、注意力 / GDN BF16、**50% 预算 / 128 个并发序列上限**，GPU 1 / `18082`，KV / 状态预算 3.99 GiB。用户先授权部署 40%，随后要求扩大缓存，扩容及验收已完成；见 [最新缓存扩容记录](cache-expansion.md)及 [此前 40% 部署记录](deployment.md)。以下记录更早在独立 GPU 2、模型端口 `18092` 的两档部分量化及低预算试验；试验期间正式服务保持原 INT4 配置。

## 权重来源

`mlp_only` 仅保留 96 个 MLP 投影模块的 INT4，普通注意力和 GDN 投影恢复原始 BF16；`gdn_bf16` 保留 128 个 MLP / 普通注意力投影模块的 INT4，仅恢复 GDN 投影的 BF16。两者均保留原始 embedding、视觉、归一化等浮点权重。

INT4 tensor 复用已校准的 Intel AutoRound 固定 revision `0a857215cab37e8caa857a053005a73cf98ff2c4`。浮点 tensor 原样取自原 BF16 checkpoint，没有把 INT4 反量化后假称恢复精度，也没有重新校准。这里只验证两种模块划分，尚不能确定哪些层对工具调用最敏感。

导出按 safetensors 索引读取权威分片，以 8 MiB 块流式复制，逐 tensor 读回 SHA256 验证。发布量化分片中相同 tensor 的重复副本经哈希核对一致，输出依照索引去重。分词器、聊天模板及处理器资产保持原服务文件摘要。清单见 [MLP INT4 来源](mlp_only-source.json)和 [GDN BF16 来源](gdn_bf16-source.json)。本机不加载模型，导出和推理均在服务器执行。

vLLM 0.24.0 的 INC 配置通过 `block_name_to_quantize` 指定量化模块，其余投影使用未量化的执行方法；本轮保持合并投影的配置一致，并实际核验模型加载和 Marlin 内核。依据为当前部署 commit 的 [INC 配置解析](https://github.com/vllm-project/vllm/blob/ee0da84ab/vllm/model_executor/layers/quantization/inc/config_parser.py)和 [INC 执行实现](https://github.com/vllm-project/vllm/blob/ee0da84ab/vllm/model_executor/layers/quantization/inc/inc.py)。

## 对照方法

保留 16384 上下文、BF16 激活、prefix cache、XGrammar strict、紧凑 JSON、原始 Java JAR、提示词、工具定义和真实 Recommend / RAG / Catalog 依赖。使用本次独立 Java 容器及 loopback 捕获代理，不修改共享业务服务。捕获请求不含鉴权头，完整请求、响应和账号副本仅存远端私有目录，公开报告只包含计数与性能结果。

三条单轮请求各执行两次，再执行一组两轮请求，共八条实际业务：基础鼠标推荐、静音办公鼠标及理由、编程键盘及区别、换一批办公鼠标。通过条件包括最终回答结束、五件合法目录商品、复杂请求说明文字以及内部工具记录无 FAILED；这些属性不代表所有推荐理由均语义正确。

当前实际业务请求的温度经捕获确认为 `0.1`，业务对照保持该配置。另冻结八个真实规划输入，每个分别以 seed 0、1 重放，共 16 次配对；各模型使用同一 payload 哈希及相同 seed，保留温度和输出预算，只改为非流式读取完整结果。检查工具 schema、RAG 查询参数及结束状态；不执行重放产生的工具调用，所以它不替代完整业务验收。seed 控制降低采样差异，不能保证跨运行环境所有计算完全确定。

启动还包含七类结构化 / 工具探针及八路并发，再执行 90 个直连请求和六项内容属性回归。固定 128 tokens 的测试刻意生成到长度上限，不能把该项的 `length` 当作完整业务失败；实际规划请求必须正常结束。

## 已确认的既有失败

此前当前 INT4 的静音办公鼠标样例曾出现一次 `rag_support` FAILED。原 trace 显示第二次调用带商品 ID、providers 等字段，但没有 query；记录中的错误正文为空，尚不能由此确认全部失败都由量化精度或某个 HTTP 服务造成。脱敏参数形态见 [既有失败](partial-baseline-failure.json)。

本轮当前 INT4 的八条完整业务通过 8/8；固定规划重放仍有 2 次 RAG 查询缺失、4 次未完整结束，工具 JSON 的 schema 错误为 0。两次查询缺失均属于四次长度截断中的调用，不能相加为六次独立失败，也不是完整调用漏参的证明。这说明结构化解码通过与工具参数适用、规划完成是不同的检查。结果见 [业务控制组](control-business.json)和 [固定规划控制组](control-planning.json)。

首次 `mlp_only` 启动已经加载 5.52 GiB 权重，但 50% 预算下仅有 233 个 Mamba 缓存块，不足默认 256 个并发序列，CUDA graph 初始化拒绝启动。没有提高显存预算，改为 128 个并发序列后继续验收；16K 上下文保持完整。这个容量参数差异需要在性能比较时考虑。

## 结果与运行状态

| 配置 | 权重加载 | 128 tokens 中位耗时 | 实际业务 | 业务中位耗时 | 16 次固定规划未完整结束 | 查询缺失，含截断 |
|---|---:|---:|---:|---:|---:|---:|
| 当前 INT4 / 50% | 3.73 GiB | 656.80 ms | 8/8 | 19.64 s | 4 | 2 |
| 仅 MLP INT4 / 50% | 5.52 GiB | 873.19 ms | 8/8 | 9.90 s | 3 | 0 |
| MLP、普通注意力 INT4，GDN BF16 / 50% | 5.11 GiB | 817.58 ms | 8/8 | 12.54 s | 1 | 2 |
| 仅 MLP INT4 / 40%，并发上限 64 | 5.52 GiB | 873.89 ms | 8/8 | 7.17 s | 4 | 0 |

INT4 固定长度数据来自该正式配置此前已验收的 `memory-production-model.json`，与本轮候选并非同时、同卡执行。完整业务及 16 次规划回放则是本轮重新对照。50% 的两档候选均为并发上限 128，当前正式 INT4 为默认 256；不能把表格视为严格控制全部变量的吞吐基准。

两档候选均通过启动探针、90 个直连请求、六项内容属性及八条实际业务。MLP INT4 / 50% 的业务中位耗时比本轮 INT4 控制组减少约 49.57%，GDN BF16 方案减少约 36.13%。这些顺序运行的小样本包含采样、规划路径和下游缓存等因素，不能据此承诺线上 P95 或将差异全部归因于精度。

只保留 GDN BF16 的方案，在固定回放中有一次正常 `tool_calls` 结束的 `call_agent` 未提供 query/task，另一次同样缺参的调用被长度截断。MLP INT4 方案未出现查询缺失，但仍有三次 `load_skill` 规划生成达到 1200 tokens 上限。其 RAG 支持 / 委派调用数为 6，当前 INT4 为 11，GDN BF16 方案为 9；模型选择的工具路径变化，查询缺失次数不是同等数量 RAG 调用的错误率。

完整业务的所有三档本轮均为 8/8 且工具无 FAILED，尚没有证明真实工具成功率提高。部分量化对本轮业务生成效率有改善迹象，仍未解决固定规划的过长生成或全部语义问题。

捕获到的克隆模型请求为：当前 INT4 43 次 / 20102 输出 tokens，MLP INT4 41 次 / 6145 tokens，GDN BF16 43 次 / 11884 tokens。所有捕获温度均为 0.1、无代理错误。计数涵盖经过捕获代理的模型请求，不假定它们全部属于主 Agent；下游业务依赖保持相同。

50% 预算下，隔离 GPU 2 整卡占用分别为 MLP INT4 11303 MiB、GDN BF16 11311 MiB，含运行时及缓存。MLP 方案 KV / 状态预算为 3.99 GiB，16K 请求容量估算为 6.50；GDN 方案为 4.37 GiB / 7.11。容量估算不能当成同等长度吞吐实测。当前正式 INT4 的权重为 3.73 GiB，但模型进程约占 11760 MiB；同卡还有独立 BGE，整卡约 14867 MiB。

最后对 MLP INT4 补测 40% 预算、并发上限 64，保留 16K、完整模型及同样的全部回归。启动探针、90 个直连请求、六项内容属性及八条实际业务均通过。隔离整卡实测 8761 MiB，约 8.56 GiB，比该模型 50% 预算的 11303 MiB 少 2542 MiB，约 2.48 GiB。该占用不包含正式卡上的 BGE，不能与包含 BGE 的整卡值直接比较。

40% 预算的 KV / 状态空间为 1.83 GiB、48720 tokens，16K 请求最大并发容量估算 2.97，比 50% 方案的 6.50 更小。通过的是本轮短工具请求的八路并发探针，未测试持续高并发长上下文负载。业务耗时中位数为 7.17 秒，其中同一句静音鼠标两次为 3.40 和 18.13 秒，波动仍明显。固定规划为 4/16 未完整结束、0 次查询缺失，与控制组未完整结束次数相同；没有把它称作工具可靠性修复。

该轮捕获模型请求 36 次 / 5516 输出 tokens，控制组为 43 次 / 20102 tokens。生成长度和规划路径减少是可观察结果，业务速度改善不能归结为单 token 解码变快。具体数据见 [四档汇总](comparison-summary.json)、[低显存运行状态](winner_low_memory-state.json)、[实际业务](winner_low_memory-business.json)及 [固定规划](winner_low_memory-planning.json)。

## 试验结束时的决定与保留配置

试验阶段保留 MLP INT4、注意力 / GDN BF16 的两个已验收预算配置作为候选：50% 预算保留更多长上下文容量，40% 更省显存。当时小样本未证明真实工具成功率提高，固定规划仍有失败，因此试验阶段没有替换正式服务。当时模型为原 Intel INT4 / 50% / 16K，健康、PID、`.env` 和脚本摘要的历史证据见 [试验后正式状态](production-live-state.json)。用户随后明确授权部署 40% 方案，该次切换及验收状态见 [deployment-live-state.json](deployment-live-state.json)；再后续按用户要求扩大为 50%，当前状态见 [cache50-live-state.json](cache50-live-state.json)。

当前公开配置摘要保存在 [candidate-config.json](candidate-config.json)，已随后续 50% 缓存扩容更新状态；此前 40% 运行证据仍保留。权重目录分别保留在服务器：

- `/mnt/data/luo/models/Qwen3.5-4B-INT4-MLP-BF16-sensitive-20261011`
- `/mnt/data/luo/models/Qwen3.5-4B-INT4-attn-MLP-BF16-GDN-20261011`

本次候选模型已关闭，Java 克隆、捕获代理和账号 / 环境凭据副本已清理，端口 `18092`、`18314`、`18094` 均关闭。共享 Agent、正式模型、BGE 及训练作业保持运行，原模型与账号文件未删除。清理记录见 [cleanup-state.json](cleanup-state.json)。完整请求及私有诊断证据保留在服务器受限目录，不进入仓库。

本目录控制脚本配合服务器冻结的旧夹具使用，执行导出 / 推理的路径为远端环境，不能在本机直接运行来加载模型。所有公开 JSON、Python AST、三轮相同回放输入哈希 / seed / 温度、验收状态、来源哈希及清理状态已经由 `verify_results.py` 检查通过；脚本不把 8/8 属性检查扩张成所有语义或负载保证。
