# 模型服务优化执行记录（2026-10-11）

本次优化面向现有 Qwen3.5-4B / vLLM 0.24.0 模型服务。原生 JSON Schema 短样例的完成时间由 616ms 降到 438ms；strict 工具调用基本不变。实际提示词与工具 schema 预热、八路并发结构化预热以及空闲保温检查一并部署，保留 BF16、视觉能力、16K 上下文与 GPU 1 的 0.78 显存比例。结果只覆盖本报告列出的模型接口测试，不代表完整 Agent 轮次的生产延迟。

## 对照方法与结果

在空闲 GPU 2、独立端口 18092 顺序启动对照实例，正式 GPU 1 服务在隔离试验期间继续运行。各组采用相同本地权重、16K、0.78、prefix caching、XGrammar 与 `qwen3_xml`；未改量化与 KV dtype。退出只清理本次创建的实例，并核验 GPU 2 释放。GPU 0 的训练任务、GPU 1 的 BGE 不参与切换。

正式比较采用 [baseline_repeat.json](baseline_repeat.json)，避免把首轮并发的内核 JIT 当作稳态速度。每组 110 次请求：32 次基础测试、6 次实际请求重放、52 次并发分轮测试、20 次突发及长短混合测试。并发分轮测试每个并发度运行四轮，第一轮只作预热，其余三轮纳入中位数。以下均为完成时间中位数，单位 ms。

| 场景 | 基线 | 纯文本 | 纯文本 + 4096 tokens / 16 sequences | 紧凑 JSON |
| --- | ---: | ---: | ---: | ---: |
| 短原生 JSON（6 次） | 616.27 | 616.52 | 633.38 | 438.48 |
| strict named tool（6 次） | 767.75 | 770.39 | 783.87 | 767.67 |
| 形状预热后工具，并发 1 | 770.64 | 770.50 | 786.31 | 768.94 |
| 形状预热后工具，并发 4 | 935.90 | 933.87 | 947.67 | 933.14 |
| 形状预热后工具，并发 8 | 1564.53 | 1865.66 | 1733.92 | 1550.83 |

紧凑 JSON 输出采用同一 schema，预算、类别和需求语义一致；字符串出现“非皮质”与“不要皮质”的同义表达，并非逐字节相同。去掉多行缩进后总输出由 58 tokens 降到 40，完成时间减少约 29%；首内容时间仍约 54ms。strict 工具输出仍为 73 tokens，约 768ms，未获得同等收益。并发 8 的数值差异不足以证明吞吐提升，不作此结论。数据集中只有少量确定输入，没有生产到达分布、长时间负载或 P95 SLA 验证。

原始数据：[纯文本](text_only.json)、[较小批次重试](text_only_batch_retry.json)、[紧凑 JSON](json_compact.json)、[汇总](comparison.json)、[短 JSON 需求语义检查](json-semantic-check.json)。实际请求重放采用两个已有测试请求，输入约 6.1K / 6.5K tokens；每个请求重复三次。每次检查成功 finish_reason、唯一指定工具、完整 JSON、原请求工具 schema、非空公开块及文字。只保存用量、计时与参数摘要，不保存请求正文；schema 合规不能替代完整业务事实与工具选择验收。

## 最终变更

- 启用 `VLLM_JSON_COMPACT_OUTPUT=true`，向 XGrammar 传 `disable_any_whitespace=true`。当前 vLLM 的 JSON 与 structural-tag 编译路径不同，不能把它当作所有工具参数的压缩开关。
- `VLLM_WARMUP_PAYLOAD_FILE` 可读取 1–8 个同机受保护的实际测试请求。保持 messages、tools、tool_choice 与 chat template 输入；仅调整模型、温度、流式模式、单结果及生成预算，防止另一个输出上限或最少输出长度绕过 1 token 的预热预算。不执行工具，不添加破坏前缀的 warmup 标记。正式文件持久存放于模型部署目录，权限 0600。
- 启动时执行七种原生 JSON / 工具 / 流式探针，再执行八路 named-tool 并发请求，所有响应完成校验才创建 ready。主要用于提前覆盖常见并发形状，无法保证所有业务形状都没有 JIT。
- 定时保温从第一次循环起核验运行和等待请求数，忙时跳过，指标读取失败也跳过。检查与业务到达之间仍存在竞态，不保证绝对无争抢；缓存满时仍可淘汰，动态商品枚举及历史变化时只有相同前缀可复用。业务模板更新后需刷新预热文件。
- 增加纯文本、批次上限与 speculative-config 实验入口，默认关闭或留空。MTP、FP8、纯文本与较小批次均未由本次优化启用；Java 业务代码和公开输出投影规则未在本次修改。

## 未推广的尝试

纯文本和较小批次没有稳定速度优势，因此没有用功能损失或吞吐上限交换不确定的收益。实际请求即使输入相同，在不同缓存/批次状态下也可能生成不同长度的合法文字；例如 60 与 70 tokens 的完成时间不能直接当作引擎速度差异。

另测试了要求工具输出单行 JSON 的提示词，实际工具 token 数没有下降，也没有稳定加速，未写入业务提示词。证据：[format-comparison.json](format-comparison.json)。

首次较小批次试验已通过七种探针，但更新隔离环境中的 Bash 文件时原地覆盖了正在读取的脚本，导致读取位置错位退出。这是试验基础设施失误，不能记作模型不兼容。改成上传临时文件并原子替换后重新执行，重试通过；所有正式部署文件也采用原子替换。

## 重启与验证

部署脚本先核对正式文件 SHA256、模型进程父子关系、GPU 1、BF16、16K、0.78、服务健康和空闲指标；备份启动脚本与 `.env`，再停止核验后的正式模型启动器。新脚本和私有预热文件采用同目录原子替换，从持久 `.env` 启动。失败时自动恢复文件和原配置并重新启动，不清理其他 GPU 工作负载。

本地针对预热、启动参数、readiness 与结构化并发校验的 **32 个测试通过**。最终正式重启的七种探针及八路并发探针通过，随后 **90 次模型接口请求通过**：32 次基础测试、6 次实际请求重放、52 次并发分轮测试。正式短 JSON 中位数为 438.51ms，named-tool 为 769.96ms；实际最终回答样例约 1.85s / 0.70s，格式与原 schema 校验通过。此次预热文件只包含两个最终回答测试请求，没有证明普通工具选择、RAG 或所有动态候选都完整命中缓存。

2026-10-11 11:12（北京时间）最终核验：`/health` 返回 200、ready 与八类探针报告一致、运行参数使用紧凑 JSON、部署文件与本地候选逐字节一致、私有预热文件权限 0600、`.env` 持久配置已生效、对照端口 18092 已关闭。证据：[部署状态](deployment-state.json)、[重启后请求](production-after.json)、[最终状态](final-state.json)。GPU 1 最后占用约 21655MiB，BF16 权重与 KV dtype 未改，本次并未降低预分配显存。

`deploy.py` 是本次服务器布局的单次执行脚本，包含切换前摘要检查，不能当作无条件覆盖或通用部署工具重复运行。备份目录位置在部署状态中保存；回退时应恢复对应启动文件和 `.env`，核验空闲及进程身份后从 wrapper 启动，不能直接杀死同 GPU 上的其他服务。

首次正式启动的七种探针与八路并发探针均通过，但空闲基准撞上 ready 后保温进程的首轮请求而拒绝执行，触发自动回退；原配置已恢复健康。加入验收前等待空闲的步骤后重试，并等待另一组完整 Agent 验收结束才再次切换。该过程按失败回退记录，不能把第一次启动当作最终推广成功。证据：[首次回退状态](deployment-state-attempt1.json)。另一组验收运行时的一次重试因持续有请求而在切换前退出，未改动模型实例。
