# 完整推荐编排检查与能力工具异步执行修复

本轮保持 GPU 1 模型、量化配置、提示词及工具集合不变，修复能力工具提交时同步等待的问题。改动已完成代码与独立实例验收；共享 QA / 前端使用的 Agent 没有切换到新构建。

## 已确认的问题与改动

`StreamingAgentToolUseOrchestrator` 已支持在流式检测到工具后立即提交，也会并行执行既有名单中的独立工具。然而 `AgentCapabilityToolUseExecutor.executeCapability()` 原先同步调用能力注册器，等真实推荐 / RAG HTTP 完成后才返回 `completedFuture`。因此编排器的 `submit()` 会被阻塞，后一工具无法及时提交；推荐与 RAG 能力调用也未走内部工具已有的并发许可与可中断 Future。

现在正式装配的能力工具复用 `VirtualThreadAgentToolUseExecutor` 的线程资源、工具并发许可和中断逻辑，能力注册器与审计仍执行原流程。独立工具得以重叠运行，非并行工具继续使用原依赖屏障，结果保持提交顺序。自定义执行器维持其原执行约定。没有缩小循环预算或强制省略证据检索。

本轮只修改上述两个生产类，新增四个集成边界测试。工作区原有的工具门禁、外部化和中断处理变更均保留，不能将相对于 Git HEAD 的整个差异当作本轮改动。

## 验证

先通过真实能力注册器和编排器复现失败：第一个能力任务等待结果时，第二个独立能力任务在两秒内不能启动。修复后重叠启动及结果顺序检查通过；新增测试另验证取消传递、共享工具并发上限，以及串行能力对前后任务的依赖屏障。失败证据见 [复现记录](capability-concurrency-red.json)，模块测试汇总见 [构建验证](validation.json)。

独立 Agent 实例 `18316` 使用已校验的新 JAR，连接既有 `18082` 模型与真实 Recommend / RAG / Catalog、会话数据库；会话建立、登录和目录查询使用原网关，LLM 流式对话通过独立 Agent 的受信任网关身份头进入。这是服务级真实完整推荐验收，没有改变共享网关的路由或重新测量网关鉴权耗时。

## 收益边界与后续优先级

当前模型请求设置 `parallel_tool_calls=false`，通常每次模型推理只生成一个工具调用。本次修复消除了 Java 执行边界的阻塞问题，但不能把依赖前一工具结果的多次模型规划变成并行任务，所以不会独自把完整推荐降到 300 ms。

本轮键盘请求的审计出现六次 `rag_evidence_search`，多轮请求出现三次 `call_agent`。只有名称和次数，尚不能证明它们是相同参数的重复查询；不同候选、查询、过滤条件或证据目标仍须分别执行。

后续建议按以下顺序实施，并各自验证功能边界：

1. 标明服务已经完成的召回、排序与目录事实，让模型以缺少的证据为依据规划；同一 Turn、同一有效输入的重复只读执行可以考虑复用，但不跨用户、候选、过滤条件、偏好版本或需要新交付的“换一批”请求复用最终推荐。
2. 对标准业务中确定匹配的技能由编排提前加载，完整保留技能内容、版本、审计与自定义钩子；减少只为加载技能而增加的模型往返。自定义技能和不明确的需求保留动态工具路径。
3. 记录每次检索的有效参数、证据增量和模型/工具耗时，再设计对无新增证据的收敛条件。不能仅按“已调用两次 RAG”强制结束，也不能将空结果视为已经满足需求。

独立验收容器和凭据副本已经清理，见 [清理状态](clone-state.json)。共享 QA、模型及其他训练任务未重启；本轮脚本和新 JAR 保留在服务器本次独立目录供核验。
