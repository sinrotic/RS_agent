# 本地模型量化执行与对照（2026-10-11）

后续性能优化没有满足“不退化”的推广版本，三次正式验收后均已恢复，当前仍保持下述 50% / 128 部分量化配置。[最新实测与恢复状态](../model-serving-next-optimizations-20261011/execution.md)

最新正式配置为 MLP INT4、注意力 / GDN BF16、50% 显存预算 / 并发上限 128，KV / 状态预算 3.99 GiB，正式八条业务和 16 路短工具探针通过；见 [最新缓存扩容记录](../model-partial-quantization-20261011/cache-expansion.md)。用户先授权的 40% 部署见 [部分量化部署记录](../model-partial-quantization-20261011/deployment.md)。更早 INT4 / 50% 的显存优先配置、五条业务及一次工具失败记录见 [上一轮部署](memory-deployment.md)。下文及 `deployment-state.json`、`live-state.json` 为更早的速度优先阶段，不代表当前配置。

两档部分量化及 40% 预算试验见 [工具调用对照](../model-partial-quantization-20261011/README.md)。试验阶段保留候选，用户随后授权部署；当前小样本业务通过，固定规划仍有未完整生成，没有宣称工具可靠性已修复。

速度优先阶段中，三种量化候选完成隔离对照，两种 W8A16 范围曾进行正式切换验收，最终均撤回。当时正式服务恢复 Qwen3.5-4B BF16，健康检查和结构化探针通过，五份原运行文件 SHA256 完全一致，没有保留量化配置。INT4 的固定长度生成明显更快，但保留原分词器后的完整业务复测出现工具失败；W8A16 的固定生成更快，但完整业务验收不稳定。恢复后的 BF16 同样复现复杂请求变慢，不能把业务退化单独归因于量化精度。该阶段未实现可验收的完整业务加速。

本报告针对现有 Qwen3.5-4B、RTX 4090、vLLM 0.24.0，不把参数规模 4B 解释为总显存 4GB。

## 对照条件

正式服务使用 GPU 1，与独立 BGE 共用显存；隔离实验使用 GPU 2 的 `18092`。两者均保留 16K 上下文、0.78 显存比例、视觉模型、prefix cache、XGrammar strict 工具、紧凑 JSON 与真实前缀预热。不修改业务提示词、工具定义、推荐排序、公开响应校验或其他服务容器。

同样的固定输入、温度 0、输出 128 tokens 用于比较解码速度。该项目是特意要求 `ignore_eos` 并生成到 128 的直连测试，不能将其 `finish_reason=length` 当作完整业务回答的合格结束；其他结构化请求必须正常结束、JSON 完整且字段符合要求。

| GPU 2 隔离方案 | 128 tokens 中位耗时 | 相对 BF16 耗时下降 | 模型加载显存 |
|---|---:|---:|---:|
| BF16 | 1307.59 ms | — | 8.61 GiB |
| 中间第 8～23 层 MLP W8A16，隔离重启复测 | 1164.77 ms | 10.92% | 7.60 GiB |
| 中间第 8～15 层 MLP W8A16，缩小范围 | 1237.50 ms | 5.36% | 8.11 GiB |
| Intel INT4 AutoRound，原发布分词配置 | 655.51 ms | 49.87% | 3.73 GiB |

正式 GPU 1 的切换前对照另存于 `bf16-production-latency.json`：固定 128 tokens 为 1299.77 ms，73 tokens named tool 为 768.20 ms，短 JSON 为 438.73 ms / 40 tokens。GPU 2 的短 JSON 为 42 tokens，不跨卡把这些输出长度差异称为内核收益。

实际 Agent 的总耗时还包括推荐、RAG、模型工具循环与商品补全。不同运行可能改变生成长度和调用轮次，不能直接把完整业务耗时的差值全部归因于量化，也不能由小样本给出生产 P95 或持续吞吐保证。隔离测试的主 Agent 使用 `18092`，原业务服务的 RAG 子 Agent 仍使用正式 `18082`；正式切换时两者才使用同一精度。这一差异也限制了隔离成功对正式业务表现的预测能力。

## 权重来源与分词协议

INT4 权重来自 [Intel/Qwen3.5-4B-int4-AutoRound](https://huggingface.co/Intel/Qwen3.5-4B-int4-AutoRound/tree/0a857215cab37e8caa857a053005a73cf98ff2c4)，固定 revision 为 `0a857215cab37e8caa857a053005a73cf98ff2c4`。这是 Intel 对 Qwen 模型的量化发布；配置为对称 4 位、group size 128、BF16 激活及 GPTQ 打包。五个权重文件共 4,583,501,352 bytes，已逐文件记录 SHA256，见 `int4-source.json`。实际推理走 INC / Marlin W4A16；敏感状态、归一化、视觉等仍有浮点部分，不能称整个模型每个 tensor 都是 4 位。[发布配置](https://huggingface.co/Intel/Qwen3.5-4B-int4-AutoRound/blob/0a857215cab37e8caa857a053005a73cf98ff2c4/config.json)

发布包与原模型的有效词表、BPE merges、特殊 token 和聊天模板一致，但 `tokenizer_config.json` 指定的加载类不同，当前 Transformers 产生了不同的 Unicode 分词正则及 ByteLevel 配置。六条样例 token 一致不足以证明整体协议一致，原发布包不直接作为推广候选。差异完整记录在 `asset-compatibility.json`。

`prepare_int4_runtime.py` 创建独立 `-rs-runtime` 目录，量化权重通过符号链接引用固定版本文件，保留原服务的分词器、聊天模板和已有图像处理资产；原 BF16 及原下载目录均保持完整。复核完整有效 tokenizer JSON 与原服务一致，再以这个目录重启复测。来源与资产摘要记录在 `int4-runtime-source.json`，并由推广脚本核验。

## 验收范围

每个完整候选覆盖启动的七种 JSON / strict 工具探针及一组八路并发探针，再运行 90 个模型直连请求：基础结构化 / 固定长度测试 32 个、实际最终回答请求回放 6 个、并发 strict 工具稳态 52 个。

另有六个固定内容回归样例：三条通勤背包建议的长度与主题覆盖、算术及余额正确，以及预算 / 电脑尺寸两个澄清字段含所需关键词。后两项只检查字段与关键词，人工复核发现 BF16 和量化模型均有复述用户的“预算”文本、第一人称“电脑尺寸”问题，不能将它们算作澄清语义完全正确。实际 Java 验收使用本次独立容器 `rs-quantization-20261011-agent`、loopback `18314`，保留原 JAR、账号与画像身份传递、真实 Recommend / RAG / Catalog 和公开响应投影。五个推荐 / 多轮样例必须结束、返回合法目录商品，复杂请求保留说明文字，内部工具记录没有 FAILED；这些基本属性检查不证明所有推荐理由和比较语义都正确。

BF16、W8A16 隔离重启与 INT4 首轮均通过六个固定属性样例及五个实际推荐样例。INT4 保留原分词器后的重启复测在“推荐适合编程使用的键盘，说明各自的区别”出现 `rag_support` FAILED / `CAPABILITY_EXECUTION_FAILED`，因此没有进入正式切换；仅凭该记录不能把根因确定为量化数值误差。详见 `int4-failure.json` 与 `int4_autoround_restart2-state.json`，完整私有证据留在服务器。

## 为什么模型单次更快，完整业务却退化

第 8～23 层 MLP 方案在正式 GPU 上固定生成 128 tokens 从 1299.77 降到 1165.28 ms，named tool 73 tokens 从 768.20 降到 687.04 ms。首次五条完整推荐的中位耗时却从 7534.52 增到 13862.94 ms；静音鼠标请求为 21821.77 ms，热复测仍为 22948.54 ms。编程键盘热复测 43477.88 ms 后没有完整最终回答，内部完成原因为 `MODEL_ERROR`。该方案已撤回并恢复 BF16，再开展较小范围对照。

已有 trace 显示：固定长度解码更快，但主 Agent 的生成工作量和规划路径发生了显著变化。恢复 BF16 后，在同样重启、预热及复杂输入条件下补测，也出现更多模型调用和生成 tokens。业务属性检查通过，耗时仍明显高于最初基线；因此此前将变化主要归因于量化的判断证据不足，需要更正。

| 实际请求 / 配置 | 记录到的模型调用 | 记录到的输出 tokens | 生成 1200 tokens 的轮次 | 完成时间 |
|---|---:|---:|---:|---:|
| 静音鼠标 / BF16 | 1 | 222 | 0 | 7.53 s |
| 静音鼠标 / 量化 16 层 MLP | 5 | 1411 | 1 | 21.82 s |
| 静音鼠标 / 同方案热复测 | 7 | 1479 | 1 | 22.95 s |
| 静音鼠标 / 量化 8 层 MLP | 7 | 827 | 0 | 17.34 s |
| 静音鼠标 / 恢复 BF16 后复测 | 7 | 1573 | 1 | 26.07 s |
| 编程键盘 / BF16 | 5 | 279 | 0 | 9.82 s |
| 编程键盘 / 量化 16 层 MLP | 7 | 2657 | 2 | 36.52 s |
| 编程键盘 / 同方案热复测 | 6 | 3992 | 3 | 43.48 s，失败 |
| 编程键盘 / 量化 8 层 MLP | 7 | 3954 | 3 | 47.14 s |
| 编程键盘 / 恢复 BF16 后复测 | 7 | 878 | 0 | 20.23 s |

计数限于现有 trace 记录的主 Agent `model_usage`，不把子 Agent 及未记录调用算在内。静音鼠标多出了加载推荐、证据、反馈和 A2UI 技能的规划轮次；这些 skill 名称不同，不能称为同一个工具参数的重复执行。没有反馈的请求仍选择反馈技能，表现为规划效率降低。新增调用和生成量是直接观察证据；不能仅凭这些样本精确断言浮点误差影响了哪一个 token，也不能在缺少完整工具计时的情况下排除所有工具服务波动。

工具服务无需每次执行变慢，总体也可能变慢：模型多次决定使用工具、生成更多参数并读取更多返回，会增加模型计算及工具执行总量。该工作量变化在 BF16 也出现；精度、重启运行状态、子 Agent 与既有规划稳定性的因果贡献尚未拆开。现有数据没有证明量化数值误差是根因，也没有证明工具服务器单次执行延迟增加。健康检查通过不等于业务时延已恢复到最初水平。

诊断使用已执行的完整业务差分，以及 `trace_feedback.py --candidate production-middle16.json` 的秒级记录回放，后者明确返回失败（耗时 2.896 倍）；对 `bf16-restart-complex.json` 的同一回放也返回失败（耗时 3.460 倍），确认这个反馈信号并非仅在量化下触发。不修改 Agent 规则来强行抑制新增工具，不删除技能或缩短输出预算以伪装加速。将候选推广门槛补充为完整业务中位耗时不得超过原基线 1.25 倍，量化 8 层 MLP 正式五条请求的中位耗时为 17338.51 ms，超过 7534.52 ms 的基线门槛，自动恢复 BF16。语义 / 决策稳定性和生成工作量必须一起看，JSON 可解析不足以证明服务正常或更快。

另三条“一般建议，不推荐商品”的实际应用请求在 BF16 基线已经出现返回商品的意图路由问题；通过完整验收的候选也是 0/3。它们单独记录为既有问题诊断，检查不新增回归，没有宣称该场景通过。六个直接模型语义样例不能替代应用意图路由修复。

第一次 W8A16 的业务脚本误读公开 DTO 的商品字段，导致验收脚本失败；修正为读取现有 `recommended_items` 后才重启完整复测，没有修改服务契约或模型来绕过检查。全部真实请求、账号和完整业务响应只保存在服务器 0600 私有文件，不进入仓库。

## 切换与恢复

`promote.py` 核验候选结果、六个内容属性样例、五个推荐样例、建议诊断不退化及同长度速度优势；再次核对正式运行文件摘要、进程身份、GPU 及空闲状态。正式 `.env` 先备份到 0700 目录，使用同目录临时文件原子替换，仅持久化模型路径、量化选项与独立精度缓存目录。

正式重启也必须完成真实前缀预热、所有启动探针和上述完整验收；并且同一张 GPU 上固定长度生成仍须比 BF16 更快。切换前将同型号 GPU、同候选已验收的编译缓存复制到独立持久精度目录，vLLM 仍按 config hash 选择编译产物并重新创建 CUDA graphs；这次正式验收覆盖了重启加载热缓存的路径。失败自动恢复原 `.env`、重启 BF16 并记录健康状态。已有共享前端、Gateway、BGE、训练作业与业务验收实例不停止、不修改。

量化减少权重占用后，vLLM 会按 0.78 的预算留出更多 KV / 状态缓存，总显存可能仍然接近原值。这里的 3.73 GiB 是模型加载占用，不是整套服务总显存。

速度优先阶段的最终状态以 `deployment-state.json` 的 `promoted=false` / `rollback=true` 及 `live-state.json` 的 BF16 核验为准；其中候选 `updates` 是失败尝试的配置，不是当前配置。`production-middle16.json`、`deployment-initial.json` 和 `live-middle16-state.json` 仅是第一次切换的历史证据；`production-after.json` 是第二次 8 层 MLP 的正式验收，`bf16-restart-complex.json` 是当时恢复后的两条复杂业务补测。该阶段的清理记录见 `cleanup-state.json`。后续显存优先部署已加载 INT4，当前以 `memory-deployment-state.json` / `memory-live-state.json` 为准。

控制脚本位于本目录，冻结 benchmark 和受保护的业务夹具保留在服务器 `/tmp/rs-agent-quantization-retry-20261011`；这些脚本针对该次远端环境，不能在本机直接运行来加载模型。兼容性依据见 [量化路线调查](../../research/2026-10-11-qwen35-quantization.md)。
