# Agent 与模型改造的重新对照评测

本轮按用户要求，把量化纳入优化前后对照，同时单独测量 Agent 并发编排的收益。使用真实账号、画像、推荐、DeepFM/BGE、商品目录和持久历史，没有用固定候选或规则正文替代 LLM。线上 GPU 1 的模型及共享 Agent 未切换；BF16 与量化模型在 GPU 2 的本任务临时端口 18096 顺序运行，Agent 使用临时端口 18318 和独立新 Session。

## 可以确认的结果

| 验证范围 | 改造前／控制组 | 改造后 | 样本与结论 |
| --- | ---: | ---: | --- |
| 同新版 Agent，普通完整推荐：BF16 → 部分量化模型服务 | 3.417 秒 | 2.411 秒 | 每组 3 条，均完整通过；均值减少 29.45% |
| 同 GPU 2、39 输入 tokens、固定生成 128 tokens | 1.362 秒 | 0.915 秒 | 每组 10 条，均满足长度检查；均值减少 32.80%，不是完整推荐 |
| 同新版 Agent，普通推荐的模型首 token | 176.550ms | 176.014ms | 每组 3 条，基本不变；不是用户可见首字 |
| 同新版 Agent，普通推荐的首正文区块 | 3.343 秒 | 2.337 秒 | 当前仍等待完整区块后发送，没有逐 token 正文事件 |
| 16 路同时请求，最新并发编排改造前后 | 16/32 完整通过 | 32/32 完整通过 | 每组两批，每批 16 条；通过率从 50% 到 100% |
| 16 路的合格完成吞吐 | 1.0268 次/秒 | 1.4727 次/秒 | 用通过数量除以两批合计墙钟时间，增加 43.43% |
| 16 路中成功请求的平均完整耗时 | 7.335 秒 | 9.573 秒 | 新版承接更多请求并排队；不能宣称并发下每条请求都更快 |
| 16 路窗口的模型 TTFT 均值 | 548.564ms | 796.273ms | 旧版只有 8 条进入模型，新版 16 条均进入；不是全体请求到首字的同口径体验 |
| 8 路中成功请求的平均完整耗时 | 7.749 秒 | 7.385 秒 | 两组均 16/16 完整通过，小样本减少约 4.69% |

普通推荐是“推荐鼠标”，每条仍经过真实 LLM 合成。完整耗时从独立 Agent 的 SSE HTTP 请求开始，直到最终答案及真实商品目录补齐；不包含登录、建 Session、后续历史/审计查询，也不包含浏览器、公网和网关入口认证延迟。首正文是测试客户端收到 text 类型 answer_block 的时间，不是浏览器绘制时间。

模型服务对照保持新版 Agent 构建、账号和请求序列相同。BF16 为原完整权重，部分量化为当前 MLP INT4、注意力/GDN BF16；两档服务还分别使用 78%/50% 显存预算、256/128 序列上限以及原/紧凑 JSON 输出配置。因此 29.45% 是本轮模型服务改造合计的业务观察值，不能全部归因于量化这一变量。业务输出有采样差异：BF16 正文平均 203.67 字，量化平均 225.33 字；量化组没有通过缩短正文获得上述耗时结果，但没有逐条人工判读解释语义。固定长度对照用于补充生成效率证据。

以上均为预热后的少量单请求或两批突发。没有达到 300ms 完整推荐，也未测出持续负载最大容量或生产 P95。直接模型定长测试的首 token 约 49/46ms，其输入仅 39 tokens，不能替代真实 Agent 推荐约 176ms 的首 token 指标。

## 最初版本与当前版本的整体观察

保留的最初 Agent 构建也连接原 BF16 模型重新执行了相同三条普通请求，然后与同 GPU 2 的当前量化模型及新版 Agent 对照：

| 指标 | 最初 Agent + BF16 | 当前 Agent + 部分量化 |
| --- | ---: | ---: |
| 返回答案和商品的平均耗时 | 9.610 秒 | 2.411 秒 |
| 首个模型调用 TTFT 均值 | 488.104ms | 176.014ms |
| 每条观察到的模型调用数 | 4 | 1 |
| 每条内部失败工具数 | 2 | 0 |
| 完整质量门禁通过 | 0/3 | 3/3 |
| 正文平均字数 | 30 | 225.33 |

最初版本的三条均返回了真实商品与持久历史，但均有两次 call_agent FAILED。因此 9.610 秒是包含失败工具的结果交付时间，不能称为合格完整推荐平均时间，也不计算等质量的整体加速百分比。原版本的首次预热还没有最终答案，保留在原始报告中，未混入成功样本。

另一个同当前 GPU 1 量化模型的 Agent 单独对照中，最初版本的三条结果交付平均 8.819 秒、模型调用 4 次、质量门禁 0/3；当前版本平均 2.313 秒、调用 1 次、质量门禁 3/3。它也不能作为等质量的加速比例。旧版在 BF16 和量化两个控制组中均有工具失败，不能仅根据旧版失败把原因归结为量化。

这两组观察使用当前推荐服务及数据资产，没有回退历史数据库、Recommend 构建、技能内容和数据集。因此是在当前依赖下复测旧 Agent/模型组合，不是完整复原历史所有服务的系统快照。

## 并发对照的定义与结果

并发控制组采用上次切换前的 Agent `8a8385f3…`，已包含此前普通推荐的 LLM 合成优化；配置为模型流 8 路、获取许可等待 200ms。新版为线上同构建 `4bc94fc…`，模型流 16 路、等待 15 秒、推荐流水线 4 路。两者均连接完全相同的 GPU 1 模型进程、权重和参数；测试前已经停止 GPU 2 的临时模型。

| 版本与批次 | 同时请求 | 完整通过 | 合格完成吞吐（次/秒） | 成功请求平均耗时 |
| --- | ---: | ---: | ---: | ---: |
| 旧配置，第一批 | 8 | 8/8 | 0.9563 | 7.973 秒 |
| 旧配置，第二批 | 8 | 8/8 | 0.8877 | 7.524 秒 |
| 新配置，第一批 | 8 | 8/8 | 0.9951 | 7.056 秒 |
| 新配置，第二批 | 8 | 8/8 | 0.9711 | 7.715 秒 |
| 旧配置，第一批 | 16 | 8/16 | 0.9931 | 7.421 秒 |
| 旧配置，第二批 | 16 | 8/16 | 1.0629 | 7.249 秒 |
| 新配置，第一批 | 16 | 16/16 | 1.6235 | 8.666 秒 |
| 新配置，第二批 | 16 | 16/16 | 1.3475 | 10.480 秒 |

旧配置 16 路两批共 16 条 AGENT_BUSY，新配置无该错误且 32 条质量门禁全部通过。吞吐是合格数量除以整批墙钟时间，包含随后历史与追踪核验；单条完整耗时不包含事后核验。表内按成功请求计算耗时，失败不当作快速完成，不能将旧版只服务一半请求的均值当作全体请求体验。

8 路是 8 个账号、8 个独立 Session；16 路是同样 8 个账号、16 个独立 Session，并非 16 个不同账号。这是独立 Session 突发处理测试，不测试同 Session 竞争，不推广为横向多活 Agent 验证，也不替代复杂推荐并发测试。

并发窗口的缓存查询计数与实际输入计数不相等。例如新版第一批 8 路：查询计数增加 85681、输入计数增加 52732、命中计数增加 68112，因此不能把该命中计数当作完整输入的唯一命中 token 数。原始采集器的联合一致性门禁拒绝了该推导，公开原始记录保留不变。

汇总对模型计时单独验证：每个窗口 TTFT、输入、排队和 prefill 的直方图请求数增量一致，且等于该批有最终交付的请求数；所有相关时间增量非负。两批的模型计时累计和除以对应模型请求数，可以得到引擎窗口的平均 TTFT：8 路控制组 621.157ms、新版 545.790ms；16 路控制组 548.564ms、新版 796.273ms。共享模型没有按 request_id 关联，数值不含 Agent 中等待模型许可的时间，不是网关到首字或生产 SLA；16 路控制组有一半请求被 AGENT_BUSY 拒绝，不能认为这些用户也获得了 549ms 首 token。

## 复杂推荐与多轮现状

当前 GPU 1 模型和新版 Agent 的同轮真实样本为：办公静音鼠标及理由 20.392 秒（观察到 8 次模型调用）；同会话“请帮我推荐鼠标”2.182 秒、“换一批鼠标，适合办公使用”19.870 秒、“再推荐五款鼠标，说明理由”13.451 秒，工具、商品和持久化门禁通过。原版因首轮质量不通过而停止多轮链，不能拿原版不完整链路与新版三轮求加速比例。

编程键盘区别推荐 11.737 秒，有最终回答但 BGE 排序为 0、声明 model_rank_unavailable，因此不计完整通过。此前共享 Recommend 更新后已存在该问题，本轮没有修改或回退 Recommend。上述检查只验证非空正文、真实商品、持久历史、工具状态与排序属性，不证明理由或比较语义充分；不能宣称全场景提速或所有功能均已完成质量回归。
