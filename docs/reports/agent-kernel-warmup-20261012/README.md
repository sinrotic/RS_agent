# 新版预热接入与首 token 复测（2026-10-12）

新版已接入 GPU 1 当前服务：空闲执行补热，原子安装预热脚本及启动器，在 `.env` 持久启用内核预热。模型 API PID 1614322、引擎 PID 1616131、模型权重、16K 上下文、.50 显存预算、128 sequences 和 strict 工具配置均保留，正式服务未重启。Agent / Recommend / Model / Gateway / Catalog 容器身份未变；预热之外的 `.env` 行逐行一致。

这次解决已确认的首次部分缓存命中导致 Triton JIT 尖峰。没有修改用户提示词、模型参数、工具选择、回答长度、商品数量、排序路径、Session 保存或 SSE 格式。

## 实现与接入

`vllm_prefix_warmup.py` 新增 `--kernel-warmup` 和 `--kernel-batch-sizes`，仅使用标准库。生成一条 6608 tokens 的合成长输入，再共享其前 5000 tokens，覆盖总长度 6608 / 6609 / 6610 / 6612 / 6616 的部分命中输入。实测这些路径命中 4752 tokens，剩余输入覆盖常见对齐类别。单次输出一 token，内容不保存。

另用 256 tokens 的短输入执行 1 / 4 / 8 / 16 路批次，每条生成两 token，保证经过 prefill 和一次 decode。批次预算限定在 1 至 16，禁止空列表和重复大小；验证返回的条数和生成 token 数，不把不完整输出算作预热成功。合成输入直接访问 `/v1/completions`，不执行 Agent 工具，也不产生业务 Session。

启动顺序保留原真实前缀和结构化输出探针，随后执行新增内核预热，再补回真实前缀，全部完成才发布 ready。`--keepalive` 不执行新增合成批次，保留轻量逻辑。新开关在仓库示例中默认 false，此部署持久启用 true，批次设置为 `1 4 8 16`。此前未获稳定收益的额外探针与逐前缀保温候选继续关闭。

当前服务使用新版脚本空闲补热完成，耗时约 2 秒；模型未重启。现有保温 PID 1622545 保留其原内存中的轻量逻辑；新文件在下一次正常启动加载。原启动器以同目录暂存文件原子替换，避免覆盖运行中 Bash 正在读取的文件。下一次真实生产重启未在本轮执行；启动门禁与失败清理由占位进程测试验证。

新增内核预热在每个批次和真实前缀前检查模型运行/等待请求数，出现业务或指标读取失败则中断，不发布新的 ready。检查与业务到达之间仍有竞态，已派发的短批次不能撤回，不能声称完全不占业务资源。

## 隔离冷启动验证

先在 GPU 2 建临时实例，使用同 INT4 权重、.50 显存预算、16K 上下文、32 sequences、独立空 Triton 缓存及已有 torch.compile 缓存。未停止其他服务。使用上一轮已复现的 6610 输入 / 4752 缓存命中 / 一生成 token 路径，比较两次隔离进程：

| 指标 | 旧流程首次部分命中 | 新版预热后首次部分命中 |
| --- | ---: | ---: |
| 引擎首 token | 442.087ms | 134.346ms |
| Prefill | 439.428ms | 131.650ms |
| 队列 | 0.024ms | 0.021ms |
| 正式输入路径 JIT | `_fused_post_conv_kernel` | 无 |

新版把 `_fused_post_conv_kernel` 和 `fused_sigmoid_gating_delta_rule_update_kernel` 的即时编译提前到预热阶段。后续三条同长度、同命中量的部分命中请求首 token 为 134.346 / 134.451 / 134.218ms；正式 4 / 8 / 16 路短批次也没有 JIT 事件。全部 9 个正式合成请求/批次通过，无缓存的 6608 长输入首 token 仍约 415ms，预热无法消除新输入本身的计算量。

这是已知冷路径的验证，不是业务平均增益、所有输入的上界或生产重启验收。两个隔离进程未同时运行，GPU 0 一直有训练；结束时 GPU 2 上另有不属于本任务的 PID 2293691 占用约 3.65GiB。本任务仅停止自己的临时进程组，最终该组无活跃进程，18096 端口关闭，其他进程保留。

旧证据见 [上一轮复现](../agent-prefill-diagnosis-20261012/reproduction.json)，新证据见 [cold-validation.json](cold-validation.json)。

## 正式网关推荐首 token

同当前 GPU 1 模型、同当前 Agent，测量网关 → 完整推荐 → 真实 Catalog → 持久 Session History。单请求使用相同测试 Account、新建 Session、相同“推荐鼠标”；4 / 8 路各两批，使用既有测试 Account 及不同 Session，不并发写同一 Session。不计登录及建 Session，也不保存认证信息、用户标识、商品 ID 或回答正文。

每阶段单请求 8 条、4 路 8 条、8 路 16 条，共 32 条；两阶段 64 条全部通过最终回答、五件真实唯一商品、工具无失败、DeepFM/BGE 有效及无排序降级检查。所有正式样本均保留，包括慢请求。

| 并发 | 每阶段样本 | 预热前模型首 token 均值 | 预热后模型首 token 均值 | 预热前完整推荐均值 | 预热后完整推荐均值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 8 | 191.315ms | 172.854ms | 2.151s | 2.094s |
| 4 | 8 | 319.407ms | 344.033ms | 2.615s | 2.492s |
| 8 | 16 | 508.998ms | 511.353ms | 8.186s | 7.863s |

单请求模型首 token 中位数 160.332 → 155.317ms，最低 150.437 → 147.666ms，最高 380.461 → 299.176ms。本轮单请求均值下降约 9.65%；4 路均值增加约 7.71%，8 路约相同，不能声称高并发 TTFT 已改善。每档只有两批，不用于推断容量或生产 P95/SLA。

基线前两条命中 4224 tokens，后六条 5280；新版后八条均命中 5280。首条仍有约 147ms 排队，因此不能把 9.65% 全部归因于内核预热。固定业务输入、实际上下文、候选与缓存状态也不是逐 token 恒定；这种热应用前后测量不等同于两个生产冷重启的严格 A/B。更可靠的修复证据是隔离冷路径的编译转移与正式阶段无 JIT。

此处首 token 是引擎首次生成，可为工具/JSON 语法，不是正文首字；单请求窗口恰好新增一条模型计时，未按 request_id 精确关联。并发批次各新增 4 / 8 条模型计时，时间直方图数量一致；并发 APC 查询可能与输入统计不相等，因此只独立核验时间计数。原 SSE 仍展示完成的 `answer_block`，单请求首正文区块均值 2.095 → 2.034 秒，完整推荐并未达到 300ms。
