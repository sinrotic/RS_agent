# 经过 LLM 的完整推荐优化与真实验收

本轮目标是降低真实 LLM 完整推荐的耗时，尽量接近 300ms，并保留现有功能。**300ms 尚未达到。** 已完成的 Agent 优化使普通首轮推荐复用已有召回、排序和商品事实，仍由 Qwen 生成最终回答。原模型下的热请求从一个基线样本的 14.386 秒降到 3.087 秒；重复测量中的普通热请求为 3.087 秒，复杂与多轮请求为 10～26 秒，不能宣称全场景加速。基线、失败实验、模型切换和最终结果均保留。

## 测量口径与环境

计时从真实网关收到 SSE 请求开始，到完整回答、商品卡片与会话保存完成，再取得五件真实商品的目录详情结束。登录和创建 Session 在计时之外。首个 token、最小模型调用、重复请求命中历史都不等同于完整推荐。

自有隔离环境 `rs_e2e_857e8b14` 使用真实 User、Gateway、Agent、Recommend、Model、Catalog、Scylla、MySQL、Redis，调用现有多路召回、训练过的 DeepFM、GPU 1 上的 BGE 与本地 Qwen3.5-4B。直接推荐开关关闭，LLM 合成与紧凑工具 schema 开关开启。每个新 Turn 都核验了真实 Qwen 请求；相同请求重试才允许返回已保存交付。

原模型使用 vLLM 0.24.0、BF16、16K 上下文、GPU 1 的 0.78 显存预算、前缀缓存与严格工具解析，没有启用量化。QA 新建表落在上一轮配置的 NVMe 数据目录，旧 `rs_agent` 数据表仍保留在原 HDD 挂载；本报告不能代表旧表迁移后的性能。GPU 0/2 的训练进程没有被本轮操作；训练任务自身的结束与新启动不属于本轮修改。

本轮业务构建仅部署到隔离 QA，正式 Java 业务 JAR 未替换。其他任务在验收后更新了正式模型配置，必须区分更新前后结果，不能混合归因。

## 已实现的修改

1. 在首轮普通品类、内置模板和标准钩子、已完成召回排序且商品品类/预算事实验证通过时，复用已有结果，交由 LLM 生成最终答案。带办公、静音、解释比较等额外条件，历史上下文、自定义模板、非空 UI 状态或事实不足的请求继续使用原工具流程。LLM 合成开关优先于无模型直接回答开关。
2. 内置最终答案 schema 按区块类型约束必要字段，省略不适用的 null；商品卡片仍须有效卡片集或商品 ID，比较、追问和 A2UI 仍可用，自定义工具 schema 不变。固定配置放在动态商品与证据之前，便于前缀缓存复用，原有上下文内容仍保留。
3. 标准内置循环在本轮已成功加载技能且内容与当前版本一致时，复用技能正文并移除重复加载选项。失败、技能内容更新、自定义 schema、循环和钩子保持原行为，其他工具没有被禁用。
4. 修复 `AgentDelegateProperties` 缺少标准 JavaBean getter 的配置绑定问题。修复前实际调用默认 `rs-service-recommend:18103`，忽略配置的 QA 地址；线程快照显示工具工作线程卡在 DNS 解析。修复后真正访问配置的 RAG 服务。
5. 提示模型使用服务已取得的真实商品，额外检索失败不应声称没有商品；未知属性应说明无法确认，理由或差异写入正文/比较区块。
6. 最终答案单独保留 4096 token 上限，普通工具继续使用原 1200 token 预算。SSE 的可配置默认期限改为 120 秒；延长期限只修正请求完整性，不能算作速度提升。

全局与云模型默认关闭 LLM 合成及紧凑 schema，`local-qwen` 配置默认开启。开关、部署说明与回退入口见 [应用部署说明](../../../java_agent/deploy/remote/app/README.md)。

## 原模型下完整流程结果

同一组查询，温度 0.1；小样本存在输出随机性，单样本比例不是稳定 SLA。

| 请求 | 基线完整耗时 | 最终完整耗时 | 最终 LLM 次数 |
|---|---:|---:|---:|
| 推荐鼠标，首次请求 | 31.035 秒后失败 | 6.350 秒 | 1 |
| 推荐鼠标，热请求 | 14.386 秒 | 3.087 秒 | 1 |
| 办公、静音鼠标，说明理由 | 10.962 秒 | 10.372 秒 | 4 |
| 编程键盘，说明区别 | 30.428 秒后失败 | 12.277 秒 | 5 |
| 多轮首句：请帮我推荐鼠标 | 9.879 秒 | 2.723 秒 | 1 |
| 多轮：换一批办公鼠标 | 7.131 秒 | 18.092 秒 | 8 |
| 多轮：再推荐五款并说明理由 | 6.356 秒 | 19.626 秒 | 8 |

最终 7/7 完成，中位数 10.372 秒；基线 5/7 完成，成功样本中位数 9.879 秒。**总体中位数没有下降，多轮场景仍有回退。** 修复下游配置后，真实 RAG 调用成功替代了之前的 DNS/工具失败，不能把前后复杂流程当作完全等价的模型工作量。保留完整工具能力和真实检索，尚未用强制提前结束来缩短这些请求。

8 个不同用户同时进行普通推荐，8/8 完成，中位数 8.064 秒，范围 7.570～8.626 秒。每个请求各调用一次 Qwen；这只是 8 并发验收，不是最大承载量或生产并发 SLA。

原始结果与逐请求模型耗时：[基线](baseline.json)、[基线汇总](baseline-summary.json)、[最终流程](optimized-final.json)、[最终汇总](optimized-final-summary.json)、[8 并发](optimized-final-concurrent-summary.json)。

## 主要耗时与 300ms 的限制

普通热请求 3.087 秒中，模型调用 2.792 秒，生成 236 tokens；复杂请求的模型调用累计占约 86%～95%，多轮约 93%～95%。此时继续削减 Java 调度的几毫秒，不能把完整回答降到 300ms。后续应优先减少重复工具决策和冗长结构化生成，再验证解释与约束满足情况。

观察到多轮请求重复进行 RAG 调用，返回的 `item_support` 为空。但返回对象的 `candidate_scoped=true` 是服务固定值，不证明候选范围已正确传入，`query_chars=0` 也不能由不存在的 `user_query` 字段推断真实查询为空。因此没有据此覆盖模型参数或修改检索范围。[结构探针](rag-scope-probe.json) 仅提供进一步诊断线索。

38 tokens 的极小结构化模型实验，原模型热中位数约 422ms，MTP 约 367ms，均超过 300ms；它们不含推荐、保存或商品详情。这是当前测试条件下的观测，不能当成硬件或所有模型的理论下界。[原模型实验](model-floor.json)、[MTP 实验](model-floor-mtp.json)。

在当前硬件和模型下，完整中文解释的生成仍需秒级。更接近 300ms 需要显著提高模型推理速度，或经另行产品评估改变输出职责；将 LLM 改成短分类、正文改由规则生成，会改变本次要求，不能作为已达标结果。

## MTP 对照与失败实验

[vLLM 的 Qwen3.5 官方配方](https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3.5.html) 描述了 MTP 及其延迟/吞吐权衡。测试只使用模型原生 MTP 一个预测 token，未永久修改正式配置，保持 BF16、16K、前缀缓存和显存预算。

同输入、温度 0、各四次的配对实验中，172-token 回答热中位数 1839.912→1700.164ms，60-token 回答 696.356→673.989ms；各次输出摘要一致。真实 8 并发实验的 MTP 中位数约 11.46 秒，对照约 8.55 秒，生成长度存在波动；不足以证明普遍收益，因此已恢复原模型，不将 MTP 作为默认上线方案。[配对原模型](model-bench-original.json)、[配对 MTP](model-bench-mtp.json)、[真实 MTP](mtp.json)、[真实对照](original-control.json)。

| 阶段 | 完成/请求 | 发现与处理 |
|---|---:|---|
| 原始基线 | 5/7 | 原 30 秒 SSE 期限与下游问题 |
| 仅区块 type 的 schema、所有步骤扩大预算原型 | 4/7 | 无效工具生成占满 4096 tokens；回退普通工具预算 |
| 早期 LLM 合成 | 6/7 | 卡片缺少卡片集/商品 ID；改为分类型必要字段 |
| 分类型 schema | 7/7 | 部分解释仍误报无数据；补充事实使用规则 |
| 原模型复测，配置绑定修复前 | 4/7 | DNS 原生解析可超过工具期限；修复实际服务地址绑定 |
| 最终 Agent，原模型 | 7/7 | 真实检索可用，复杂多轮仍慢 |
| 人工延迟测试首次尝试 | 0/1 | 另一项任务重启模型，代理连接被拒绝；不属于 SSE 超时证据 |

失败样本保留在 [compact](compact.json)、[synthesis](synthesis.json)、[original-control](original-control.json) 和 [慢模型失败](timeout-probe-failed.json)。[线程快照](thread-probe.json) 与 [绑定测试先红记录](delegate-binding-red.log) 对应真实配置问题。流式 logprobs 只包含部分已解析 tokens，不能以它推断多余生成全部是空白，因此本轮没有凭猜测添加空白限制配置。

## 功能验证与交付范围

[构建记录](build.json)：Agent 模块 228 个测试，227 通过、1 个依赖外部真实 vLLM 的条件测试跳过，0 失败/错误。另以真实模型完成上述 HTTP 验收。自定义工具、提示词/上下文保留、区块与 A2UI、事实门禁、技能版本变化和钩子兼容由相应测试覆盖。

[完整审计](audit.json) 检查每个新 Turn 实际调用 Qwen、五个真实且不重复的商品、DeepFM/BGE 均执行且无排序降级、交付独立、Scylla 权威记录和 MySQL 序号投影一致。相同请求重试返回相同回答/历史，不新增模型调用；反馈应用与去重通过，反馈后新推荐仍经过真实模型。删除 Redis 热键并重启后，历史和重复请求交付恢复一致。

这些检查不能替代全部提示词的语义质量评估。复杂解释仍可能有模型自身的不确定性，多轮延迟尚未改善到目标；不能承诺所有现有行为已经全面证明无回退。正式业务部署需使用已验证构建及相同开关，并重新核验真实业务数据和输出质量。
