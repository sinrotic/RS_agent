# 慢 prefill 的诊断与受控复现

结论：上一轮新版单并发 627ms TTFT、582ms prefill 的样本，与 GDN prefill 内核 `_fused_post_conv_kernel` 的 Triton 即时编译对应。临时模型只预热了一次完整长输入，没有覆盖首次部分缓存命中后的输入形状。受控实验在相同输入长度、相同缓存命中数量下复现了同一内核编译及延迟尖峰；编译完成后该工作量恢复正常。不能据此将量化模型解释为持续 prefill 性能退化。

## 历史样本的定位

`check_historical.py` 用每条窗口只增加一个模型计时的记录检查：prefill 超过 300ms 且大于后续热态中位数两倍、模型排队小于 10ms。运行一次得到失败信号：样本 0 的 prefill 582.480ms、TTFT 626.677ms、排队 0.020ms；后七条 prefill 中位数 122.861ms。该程序有意返回非零，作为历史症状的可执行判据，不改写原始记录。

`map_log.py` 对原临时量化模型的日志逐条统计模型 HTTP 请求序号，共 105 次，与预热 1 条加正式 104 条一致。第 1 次是预热；第 2 次就是正式样本 0。后者在 2026-10-11 23:42:34 出现 `_fused_post_conv_kernel` 即时编译警告。因此编译事件落在慢请求期间，不能当作已经排除的预热开销。第 13 次还出现另一种批处理内核的首次编译，进一步说明单次单请求预热没有覆盖并发形状。

vLLM 0.24.0 的 [JIT 监控实现](https://github.com/vllm-project/vllm/blob/v0.24.0/vllm/triton_utils/jit_monitor.py) 记录推理期间的首次内核编译，并说明其与未覆盖形状引起的延迟尖峰有关。该内核的 [源码](https://github.com/vllm-project/vllm/blob/v0.24.0/vllm/model_executor/layers/fla/ops/fused_gdn_prefill_post_conv.py) 属于 GDN 卷积后的 prefill 准备步骤，并非本项目量化的 MLP 权重计算。实际安装版本的调用代码和官方同版本源码均已核对。

## 受控实验

使用当前部分量化权重，在 GPU 2 的独立模型端口 18096 启动；开启详细 JIT 事件记录，仅为这个进程设置独立 Triton 编译缓存目录。旧实验的 torch 编译缓存复制到本任务目录以缩短启动，不修改原缓存。GPU 2 当时没有其他计算进程；GPU 0 的训练与 GPU 1 模型保持运行。

直接向模型发送合成 token 输入，每次只生成 1 个 token，排除正文长度和业务工具耗时。三轮依次执行完整无缓存输入、第一次部分命中、另一个部分命中。各轮的第一个 token 标记不同，防止跨轮复用业务前缀；其余内容相同。三轮第一次部分命中均为 6610 输入 tokens、4752 缓存 tokens，剩余处理量均为 1858 tokens。

| 首次部分命中路径 | 输入 tokens | 缓存 tokens | prefill | 模型 TTFT | JIT 事件 |
| --- | ---: | ---: | ---: | ---: | --- |
| 第一轮 | 6610 | 4752 | **439.428ms** | 442.087ms | `_fused_post_conv_kernel` 编译 |
| 第二轮 | 6610 | 4752 | **127.028ms** | 129.966ms | 无 |
| 第三轮 | 6610 | 4752 | **127.151ms** | 129.781ms | 无 |

三次排队均约 0.02ms。相同工作量在内核热态后的 prefill 平均 127.090ms，第一次多约 312ms，并且只在第一次记录到该内核编译。历史慢请求和受控实验都指向相同机制；受控实验没有复原原业务模型输入，因此不能把历史 582ms 的每一毫秒都归因于这一项，也不能把合成输入的 130ms TTFT 当作真实推荐的平均延迟。

第二种部分命中的合成请求实际也命中 4752 tokens，没有达到预想的 5280；真实计数保留，不修改为预期值。主要比较仅使用三轮第一次部分命中，它们的输入量、命中量和生成长度严格一致。

`check_warmed.py` 检查工作量一致、第一次出现相同 JIT 编译且满足尖峰判据、后两次 prefill 小于 300ms 且无新编译，结果 PASS。历史异常仍保留，不能用诊断后的热态请求替换简历报告中的慢样本来提高指标。

## 改进方向和边界

应在新模型进程正式接流量前增加预热覆盖：除完整长输入外，再覆盖部分前缀命中、不同剩余输入的对齐类别，以及实际常用的并发批次。预热应观察推理期间 JIT 事件和各路径延迟是否稳定；不能只凭一次成功回答或 HTTP 健康就绪判断所有路径已热。前缀 KV 缓存与 GPU 内核编译缓存是不同资源，前者命中不保证后者已准备完毕。

本轮只诊断和验证预热覆盖效果，没有修改线上预热流程、模型权重、服务配置或业务功能，不宣称已经完成生产部署修复，也不保证所有未知形状均不会再编译。

## 初始化问题及清理

第一启动尝试因发现健康检查空响应解析问题而主动停止，未产生正式推理样本；第二尝试因缓存重置开发接口未开放返回 404，随后清理，同样未产生推理样本。修改本任务测试脚本后，第三次改用不同前缀标记完成九个推理请求。启动尝试和错误分别保留，没有混入性能计时。未开放任何线上开发接口。

最终 `audit.json` 确认线上模型 PID 和共享服务身份不变、六个业务服务均 UP、本任务临时模型停止、18096 关闭、临时 GPU 进程组不存在。详细 JIT 仪表只在临时进程启用，进程已清理；未保存账号、令牌、原业务提示词或答案正文。
